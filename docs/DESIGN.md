# Shosa (所作) 設計メモ

動きをテキストで書き、コンパイルして人形の動きにする言語の試作。拡張子は `.shosa`。
Lily# が楽譜に対してしていることを、身体の動きに対して行う。

名前は「所作」から。能では舞を分けた動きの最小単位をこう呼び、型付 (舞の記譜) に従って並べる。

## 1. パイプライン

```
text ──▶ SyntaxTree ──▶ MotionIr ──▶ MotionClip ──▶ PNG / HTML / JSON / BVH
        (Syntax/)      (Semantics/)  (Motion/)      (Output/)
         SH0xxx          SH1xxx        SH2xxx
```

各段は前段から作られる不変の値で、`ShosaCompilation` が一か所でつなぐ。診断は層ごとに番号帯を分ける。

| 段 | 役割 | Lily# での対応 |
|---|---|---|
| SyntaxTree | 損失のない構文木。語彙を知らない | Parser / Syntax |
| MotionIr | 「どの部位が、いつ、どこへ」。JSON になる | Semantics / Music |
| MotionClip | 全フレームの全関節位置と、同じ姿勢を表す全骨の回転 (9 節) | Svg / Rendering (浄書) |

## 2. 言語サーバーと Roslyn を前提にした決定

1. **赤緑木**。緑ノードは位置を持たず不変、赤ノードは位置つきの遅延ビュー (`Green.cs`, `SyntaxNode.cs`)。
   空白とコメントはトークンのトリビアに入り、`ToFullString()` は常に元のテキストと一致する。
2. **パーサーは例外を投げず、トークンを捨てない**。足りないものは幅 0 の欠落トークン、
   置けないものは `Error` ノードになる。打ちかけのファイルにも木がある。
   - 閉じ忘れたトラックは次の `名前 {` で打ち切る (次のトラックを巻き込まない)。
   - 行末の `.` は次の行の語を取らない (補完が次の語を出す位置)。
3. **文法は語彙を知らない**。`left.fwd` も `turn.left.quarter` も構文上は「`.` でつないだ語」。
   意味はバインダーが `Vocabulary.cs` の表で決める。語を足しても文法は変わらず、
   補完・ホバー・AI 向け文法書は同じ表から生成できる。
4. **字句解析は行をまたぐ状態を持たない** (コメントも文字列も行末で終わる)。
   これが差分再パースの健全性の根拠になっている。
5. **差分再パース** (`SyntaxTree.WithChange`)。最上位の項目 (ヘッダー行、figure、phrase、form) 単位で
   緑ノードをそのまま引き継ぐ。再利用の条件は「診断がなく、改行で終わる」こと。
   乱数編集で全文パースとの一致を試験している (`SyntaxTests`)。
6. **ソース位置は最後まで運ぶ**。IR の各セグメントと Clip の `Spans` が元の語の範囲を持つ。
   プレビューで演じている語が光り、語をクリックするとその時刻へ飛ぶ。
7. **診断は範囲・番号・直し方を持つ**。`SH1011` (腕に `left` と書いた) は書くべき語を示すので、
   そのままクイックフィックスになる。

未着手で、設計上の置き場所だけ決めてあるもの:

- **型つき構文ノード**。今は汎用の `SyntaxNode` 一種類。文法が固まったら、Roslyn の `Syntax.xml` と同じく
  宣言から緑・赤のクラスを生成する (Roslyn のソースジェネレーターを使う箇所)。
- **求解の差分化**。フレーズは「入口の状態 (足の位置・向き・各部位の姿勢) → 出口の状態」の関数にできる。
  緑ノードの同一性と入口の状態をキーにキャッシュすれば、編集したフレーズ以降だけ解き直せる。
  今の `FigureSolver` は全体を一度に解く。
- **言語サーバーの残り**。ホバーの小さな姿勢図、セマンティックトークン、コードレンズ (フレーズを再生)、
  クイックフィックス (`SH1011` の語の置き換えなど)。できている部分は 8 節。

## 3. 言語

```
title "Walk"
tempo 100
time 4/4

figure a "Walker" { rig humanoid }

phrase Walk {
  a {
    steps { left.fwd right.fwd left.fwd right.fwd | left.fwd right.fwd left.fwd together }
    arms  { side:2 down:2 | hold:4 }
  }
}

form { Walk }
```

- **トラック** = 身体の部位ごとの列。ラバノーテーションの譜表の列に当たる。
  `steps` (体重と足)、`arms` `leftArm` `rightArm`、`leftLeg` `rightLeg` (体重のない脚)、`torso`、`head`。
- **イベント** = `目標[:拍数][@様態]`。目標には、その長さの**終わり**に到達する。長さの既定は 1 拍。
- **目標** = 方向の語を `.` でつなぐ。方向 (`fwd` `back` `side` `across`、体幹は `left` `right`) と
  高さ (`low` `mid` `high`)、単独の `up` `down`。腕は身体の場所 (`hip` `chest` `shoulder` `head`) も取れる。
- **`side` / `across`**。腕と脚は左右でなく「正中線から離れる / 越える」で書く。
  だから `arms { side }` の一語が両腕に正しい。
- **足** = `足.方向`。位置はもう一方の足 (支持足) からの相対。`together`、`turn.left.quarter`、
  `jump.apart`、`both.low` (膝を曲げる)。
- **`|`** は小節線。拍数が合わなければ `SH1002`。
- **`repeat N { }`**、`form { A B*2 }`。

## 4. 手順 1 (実装なしでサンプルを書く) で分かったこと

- **半円は中間点を書く必要がある**。`down` から `up` は正反対で、前回りか横回りかが決まらない。
  記譜の世界でも中間の方向を書く。黙って選ばず `SH2001` で指摘する。
- **ボックスステップは「前・横・閉じる」**。足を支持足からの相対にしたので、踊り手の言い方のまま書ける。
  絶対座標や「前斜め」にすると書き方が割れる。
- **お辞儀は体幹を一本の肢として書ける**。`torso { fwd.high }` で 45 度。専用の語は要らなかった。
- **頭だけは体幹に相対**。お辞儀で顔が前を向いたままになるのを避けるため。腕と体幹は重力基準。
- **決めきれていない点**: 歩くときの自然な腕振り (書かせるか、様式として自動で足すか)、
  手拍子など部位どうしの接触、二人の接触、視線の対象 (`look at b`)、反対側で繰り返す `mirror { }`。

## 5. 求解器 (今の版)

物理も学習モデルも使わない。閉じた式の曲線と 2 関節の逆運動学だけ。

- 足: 着地点は支持足からの相対で決まり、遊脚は弧を描く。接地中の足は動かない (試験あり)。
- 体重: 着地の瞬間ごとに「両足の間、新しい足寄り」を鍵にし、形状保存の 3 次補間で結ぶ。
  歩行では骨盤が等速で進み、左右に揺れる。片脚を上げている間は支持足の上へ寄る。
- 高さ: 両足に脚が届く範囲で最も高く。大股なら自然に沈む。
- 跳躍: 滞空時間から高さが決まる (h = gT²/8)。テンポを上げれば低くなる。
- 検査: `SH2002` 脚が届かない、`SH2003` 速すぎる、`SH2004` 両足が床を離れる。

これは「語彙が見られる動きに解けるか」を確かめる版。質を上げる段では、この位置に
学習済みのモーションモデルを「演奏者」として差し込む (Lily# の DiffSinger と同じ位置づけ)。
IR が境界なので、言語側は変えずに済む。

## 6. 確かめ方

```
dotnet test Shosa.slnx
dotnet run --project Shosa.Cli -- sheet   samples/walk.shosa -o out/walk.png    # 連続写真と床の俯瞰
dotnet run --project Shosa.Cli -- preview samples/walk.shosa -o out/walk.html   # ソースと連動する 3D
dotnet run --project Shosa.Cli -- ir      samples/walk.shosa                    # 中間表現
```

`sheet` は `--step 0.5 --from 8 --to 16` で間隔と範囲を選べる。
`shosa grammar -o docs/GRAMMAR_FOR_LLM.md` は AI 向けの文法書を語彙表から作り直す (試験が一致を見張る)。

## 7. 手順 6 (AI に書かせる試験) の結果

文法書だけを読ませた 2 体に、振付 3 本と局所修正 1 件ずつを書かせた (`trials/A`, `trials/B`)。
8 ファイルすべてが診断なしでコンパイルでき、出た診断は警告 1 件 (`SH2003`) だけだった。

直したもの:

| 見つかったこと | 対処 |
|---|---|
| `.high` の次の、高さを書かない一歩がつま先立ちのままだった | 高さを書かない一歩は普通の高さに着く |
| つま先立ちの足が足跡に描かれなかった | 足跡はつま先が床にあるかで判定 |
| `@sharp` が最初から全速で、拍の直後のコマですでに動いていた | 前半で着いて止まる、両端をなめらかに。最高速度は半分 |
| 連続写真が拍ちょうどでなく最寄りのフレームを写していた | フレーム間を補間して拍ちょうどを写す |
| `back` が 0.4 m で、文法書の「一歩」(0.5 m) と違った | `fwd` と同じ 0.5 m。前 2 歩・後ろ 2 歩で元に戻る |
| 後ろ交差の語がなく、`back.across` が一歩ぶん後ろへ下がった | `back.across` は支持足のすぐ後ろ (0.12 m) |
| `together` に高さを書けなかった | `together.high` など |
| 横曲げで腕が垂直のまま残る (部屋基準)。腕 2 本を別々に三角法で書いていた | `@body` で体幹基準にできる。既定は部屋基準のまま |
| 半拍の動きが 1 拍おきの連続写真に写らず、確認用の一時ファイルを作っていた | `--step` `--from` `--to`。文法書に間隔の規則を明記 |
| 肩の線が腕の色で、曲がった上腕に見えた | 体幹の色にした |
| 文法書の不足: figure の書き方の例、片脚立ちの体重の規則、膝上げの書き方 | 追記 |

腕の既定を体幹基準に変える案は採らなかった。前屈で「腕を垂らす」が `fwd` になってしまうため。
記譜の慣習 (部屋基準が標準、身体基準は指定したとき) と同じにした。

残っている不足 (語彙の設計が要る):

- **ステップしながらの回転**。回るワルツは、回転を半拍に押し込むしかなかった。
- **接触**。手拍子、握手、相手の肩に手。
- **繰り返しの一部だけ変える**。`Combo*2` の 2 回目だけ変えるには、フレーズを複製するしかない。
- **開始姿勢**。最初の構えに 1 拍以上かかる。
- **腕の目標の不足**。あご (ガード)、身体の前で両手を合わせる、肘の向き。
- **体幹の角度が 45 度刻み**。60 度の礼が書けない。
- **図どうしの関係**。「相手に向かって」は座標で書くしかない。

## 8. エディター (手順 7)

```
VS Code ──(LSP, 標準入出力)── Shosa.Lsp ── Shosa.Core
   │                              │
   │                              └─ shosa/clip 通知: 編集のたびに解いた動きを送る
   └─ webview (dist/preview.js): 動きを描くだけ。構文は知らない
```

- **`Shosa.Lsp`**。`LanguageServer` は「メッセージを受けて、コールバックで返す」だけのオブジェクトで、
  入出力は `Program.cs` が受け持つ。試験はオブジェクトに直接話しかける。
  - 編集は範囲で届き、`SyntaxTree.WithChange` に渡す (触っていないフレーズは再パースしない)。
  - 補完とホバーは同じ関数 (`Words.ForTarget`) を引く。その場所に来られる語は語彙表から決まる。
    `left.` の後には足の方向と高さ、`arms { side.` の後には `across` (逆向き) を除いた語が出る。
  - ホバーは語の意味に加えて「何小節目の何拍目から、何拍かけて」を出す (IR がソース位置を持つため)。
- **`editors/vscode`**。拡張本体 (`src/extension.ts`) は薄い。サーバーを起こし、プレビューを開き、
  3 種類のメッセージを運ぶだけ。
  - サーバー → プレビュー: 解いた動き (編集のたび)。見ている時刻は保つので、語を直すとその姿勢が変わる。
  - エディター → プレビュー: カーソル位置。その語の**終わり**の時刻へ移る (語が指す姿勢がそこにある)。
  - プレビュー → エディター: 演じている語 (ハイライト)、クリックした肢の語 (そこへ飛ぶ)。
- 開発時は F5 (`.vscode/launch.json`)。サーバーは `Shosa.Lsp/bin/Debug` のものを使う。
  配布時は拡張の `server/` に置く (未着手)。

連続写真は左が青、右が赤。鏡像の間違いが一目で分かる。動画を見られない書き手 (AI、試験) は
この 1 枚で動きを確かめる。

## 9. 回転つきの骨格と BVH (第 1 段階の 1 と 2)

```
shosa bvh samples/walk.shosa -o out/walk.bvh      # メートル。--scale 100 でセンチメートル
shosa bvh samples/duet.shosa -o out/duet.bvh      # 人形が複数なら duet.a.bvh, duet.b.bvh
```

求解器は関節の位置で考えたままにし、**位置から回転を読み取る段を後ろに足した**
(`Skeleton.Rotations`)。求解器の式も、位置を使う連続写真・プレビュー・試験も変えていない。

- **骨の表は 1 か所** (`Skeleton.Bones`)。17 本。名前は VRM の人型 (`hips` `spine` `chest` `neck` `head`
  `leftUpperArm` …) で、休止姿勢は +z を向いた T ポーズ、+x が人形の左。glTF と `.vrma` も同じ表から書く。
- **ねじれは曲がる面から決める**。位置だけでは、肢が自分の長さの軸まわりにどう回っているかが決まらない。
  肘・膝の曲がる面の法線を蝶番の軸とし、休止姿勢での蝶番の軸 (肘は左が -y、右が +y。膝は +x) に合わせる。
  前腕とすねの回転は、親に対して蝶番の軸まわりだけになる。まっすぐな肢は、求解器が曲げる向き
  (`Rig.ElbowPole` `Rig.KneePole`。求解器と共有) を使う。
- **`spine` は長さ 0 の骨**で、`hips` と同じ位置から始まる。求解器は骨盤の点を中心に体幹を傾け、
  股関節は水平のまま残す。`hips` は向き (ヨー) だけ、傾きは `spine` に入れると位置が正確に再現できる。
  `chest` と `neck` は回らない。
- **足**はつま先の方向を向き、左右には傾かない。求解器はかかとを上げると足を少し伸び縮みさせて描くが、
  骨は伸びないので、つま先は方向だけが一致する。
- **回転は `ClipFigure.Rotations`** (骨ごとの四元数、親に対する回転)。JSON には出さない
  (プレビューは位置で描き、編集のたびに送られるため)。
- **BVH**。チャンネルは `Zrotation Xrotation Yrotation`。ルートの `OFFSET` は 0 (位置チャンネルに
  足すかどうかが読み手で割れるため)。角度は前のフレームに近い値へ寄せ、360 度の折り返しをなくす。
  1 ファイルに 1 骨格なので、人形ごとに別のファイルにする。

試験 (`SkeletonTests`): 回転から順運動学で求めた関節が求解器の位置に 1 mm 以内で戻る。
BVH を形式の定義から書いた読み手で読んでも同じ。1 フレームで 45 度以上回る骨がない
(曲がる面を逆に読むと肢が半回転ねじれる。棒人形では見えず、メッシュで見える)。

Blender 5.3 で確かめた結果 (2026-11-14。`walk` `taiso` `kick`):

```
shosa clip samples\walk.shosa -o out\blender\walk.clip.json
blender -b --python tools\blender_check.py -- out\walk.bvh out\blender\walk.clip.json out\blender\walk [人形の番号] [フレーム...]
```

`tools/blender_check.py` は BVH を読み込み、全フレームで骨の位置を求解器の関節と比べ、
骨ごとに平たい箱を付けて数コマを描く (左が青、右が赤。箱が平たいのでねじれが見える)。

- 読み込みの既定 (Forward -Z、Up Y) のままで人形は立ち、Blender の正面 (-Y) を向く。
- 骨の位置は求解器と全フレームで 0.14 mm 以内 (BVH の小数 4 桁の丸めの範囲)。
- 長さ 0 の `hips` は、読み込みが上向き 0.1 m の骨にする。`spine` は同じ点から始まり、動きに影響はない。
- 膝は前へ、肘は後ろ・外へ曲がり、腰に手を当てる姿勢や蹴りでも肢のねじれは見当たらない。
- シーンの終了フレームは 250 のまま (読み込みは短い動きに合わせて縮めない)。
- Blender は相対パスの描画先をドライブの根から解決する。スクリプトは絶対パスに直している。

まだ見ていないのは、皮膚のあるメッシュ (VRoid など) に載せたとき。箱では手首・足首・肩の
ねじれによる皮膚の崩れは分からない。第 1 段階の 4 で見る。

開発時の注意: VS Code が言語サーバーを起こしていると `Shosa.Lsp\bin` がロックされ、
`dotnet build Shosa.slnx` が失敗する。`dotnet build Shosa.Tests -o <別の場所>` でビルドし、
`dotnet test <別の場所>\Shosa.Tests.dll` で試験できる。

## 10. glTF と VRM Animation (第 1 段階の 3 と 4)

```
shosa gltf samples/duet.shosa -o out/duet.glb     # 人形が複数でも 1 ファイル。-o x.gltf ならテキスト (データは埋め込み)
shosa vrma samples/walk.shosa -o out/walk.vrma    # 人形が複数なら duet.a.vrma, duet.b.vrma
```

どちらも `Gltf.cs` の同じ関数が書く。Shosa の座標 (メートル、y が上、右手系、人形は +z を向き +x が左) は
glTF と VRM 1.0 の座標そのものなので、骨盤の位置も四元数も変換せずに書く。

- **ノードは `Skeleton.Bones` の 17 本**。`translation` が休止姿勢での位置、回転はなし (T ポーズ)。
  アニメーションは 1 つで、`hips` の `translation` と全部の骨の `rotation` を毎フレーム持つ (`LINEAR`)。
  四元数は前のフレームと同じ符号の側に寄せる (4 つの数をそのまま混ぜる読み手のため)。
- **glTF にはスキンを付ける (メッシュはない)**。Blender はスキンが名指ししたノードだけを骨にし、
  スキンがないと空のオブジェクトの列になる (Godot も同じはずだが確かめていない)。逆バインド行列は休止位置を原点へ戻す平行移動だけ。
- **glTF は人形ごとに親ノードを 1 つ置く** (名前は人形の ID。骨のノードの後ろに並べる)。
  骨盤どうしが同じ親 (シーン直下) を持つと、Blender は 2 体を 1 つのアーマチュアにまとめてしまう。
- **`.vrma` は glb に `VRMC_vrm_animation` 拡張を足したもの**。`humanoid.humanBones` で 17 本の骨のノードを指す。
  1 ファイルに人型 1 体。スキンも親ノードも付けず、`hips` をシーン直下に置く。
- 末端 (頭、手、足) の先は glTF に書く場所がない。読み手が長さを決める。動きには影響しない。

試験 (`GltfTests`): 形式の定義から書いた読み手で glb を読み、順運動学で求めた関節が求解器の位置に
1 mm 以内で戻る。テキスト形式とバイナリが同じデータを持つ。`.vrma` が 17 本を名指しする。四元数が単位長で符号が飛ばない。

Blender 5.3 で確かめた結果 (2026-11-14。`walk` `taiso` `kick` `duet`)。`tools/blender_check.py` は拡張子が

## 11. 表記の基本規則の案 (ユーザーとの議論、2026-11-14。未決定)

**基本の規則は 2 つ。**

- 動きを書くと、書いた音価で、その動きを始めから終わりまで行う。
- 休符を書くと、その間は動きが止まる。

今の `語:拍数` と `hold:拍数` がほぼこれにあたる。違いは、今の語が**着く先の姿勢** (`side.high`) で、
案の語が**始めから終わりまでの一連の動き** (「手を振る」「蹴る」) である点。両立できる:
一連の動きを「姿勢の列に名前を付けたもの」として定義し、書かれた音価に合わせて全体を伸び縮みさせる。
第 2 段階の「ポーズの定義」を、姿勢だけでなく動きにも広げる形になる。動きをどう定義するかは未決。

**この 2 つに添えるもの。**

| 点 | 内容 | 今の Shosa |
|---|---|---|
| 並行する段 | 足と腕が別のリズムで動く。1 本の列では書けない | `steps` `arms` `rightLeg` などの段。音楽の声部と同じ |
| 休符の意味 | 体に「何もない」はない。休符は「今の姿勢のまま止まる」とし、「自然な姿勢に戻る」は動きとして書く (片足を上げたままの休符が書ける) | `hold` が前者 |
| 動き方 | 始めと終わりと長さが同じでも、鋭く止めるか、なめらかに着くかで別の動きになる | `@sharp` `@smooth` `@linear` |
| 拍に合う瞬間 | 音符は鳴り始めが拍に合うが、踊りの決めは着いた瞬間が拍に合う | 着く瞬間が音価の終わり。音楽と合わせるときに意識して決める |

音価の規則で決まらないもの (語彙の側で持つ): 向き、移動、体重がどちらの足にあるか、相手や物との接触。

**物理に従うか無視するかを `@` で書く案。**

- 既定は物理に従う。無視するほうを `@` で書く (名前の候補: `@free` `@float`)。今の求解器がすでに
  物理に従う側で (跳躍の高さは滞空時間から決まる)、診断 (`SH2003` `SH2004`) が AI の書いたものを直す手がかりだから。
- 無視できるのは力学: 重力 (跳躍の高さと滞空時間の関係)、速さの限界、体重の支え。
  無視できないのは形: 骨の長さ (`SH2002`)。骨は伸びない。
- 範囲: 語に付ければその動きだけ。ずっと浮いている人形のために、`figure` の宣言にも書けるようにする。
- 使いみち: 二段ジャンプ、空中で止まる、スローモーション、浮く人形。ゲーム向けに効く。
- 今の求解器は物理を計算しておらず、数本の規則があるだけなので、無視は「その規則と診断を外して
  指定どおりに補間する」で済む。第 3 段階のモデルは人の動きから学んでいるので、物理に合わない指定を
  守らない可能性がある。無視する語はモデルに渡さず今の求解器で動かす、という切り分けが要りそう (未実験)。

### 12.1 全体の形

```
[music "song.lys"]  または  [tempo N] [time N/N] [fps N]
[figure 名前 "ラベル"] …             振付の持ち主。1 体だけなら書かない
[dancer 名前 体 on figure …] …       踊る体。書かなければ既定の体
pose 名前 { 段 { 目標 } … }          名前の付いた姿勢
move 名前 { 段 { イベント … } … }    名前の付いた動き
section 名前 [loop] [inplace] { … }  時間の 1 区切り (今の phrase)
[form [名前] { A B*2 }]              並べる順
[score [名前] { form … dancer … }]   出力の単位 (12.8)。書かなければ既定の 1 つ
```

Lily# と語をそろえる。時間の区切りは `section` (今の `phrase` を改名)、並べる順は `form`、
演じる者は `singer` / `dancer`。曲を参照したとき `section Verse` が両方のファイルで同じ時間を指す。

### 12.2 音価の規則

- **イベント = `語[:長さ][@様態…][!印]`**。動きは書いた長さの始めから終わりまで行い、**終わりに着く** (今と同じ)。
- **`hold`** = 今の姿勢のまま止まる (休符)。**`skip`** = この段は何も言わない (LilyPond の `s`。下の「段の重なり」で使う)。
- **長さの単位**。`:2` は拍、`:0.3s` は秒、`:12f` はフレーム (`fps`、既定 30)。秒とフレームはテンポで拍に直して
  小節線の検査に入る。Lily# の音価 (`4` = 4 分音符) は採らない。踊りは拍で数え、語に数字を直に付けると読みにくい。
- **`:0`** = 時間をかけずにその姿勢にいる。使えるのはクリップの先頭だけ。**開始姿勢**はこれで書く
  (`body { guard:0 jab … }`)。専用の構文は足さない。先頭の `:0` は、どの段のものも、長さのあるイベントより先に効く
  (`body { guard:0 }` と `torso { back.70:0.2s … }` を並べると、構えた形から体幹が動く)。
  `loop` の `section` には要らない (始まりの状態は終わりの状態なので、`body { guard:8 }` で構えたままになる)。
- 拍に合う瞬間は「着く瞬間」。1 拍目に決めたい動きは、その前の拍から書く。曲に合わせるときは
  セクションの弱起 (Lily# の `partial` にあたるもの) で前に出す。

### 12.3 姿勢と動きの定義

```shosa
pose guard {
  steps { left.fwd.low@small }
  arms  { fwd.high@bent }
}
move jab       { leftArm  { fwd:1@sharp!hit  guard:1 } }
move cross     { rightArm { fwd:1@sharp!hit  guard:1 } }
move frontKick { rightLeg { fwd.low:1@bent  fwd:1@sharp!hit  fwd.low:1@bent  down:1 } }
```

- `pose` は段ごとに目標 1 つ、長さなし。`move` は段ごとにイベントの列。
- **`pose` は形で、動きではない。** すでにその形なら何も動かない。`steps` の行は「その一歩を踏み終えた立ち方」
  (両足の位置関係、高さ、体重) と読む。段に直に書いた `left.fwd` は毎回踏み出すが、`guard` の中の `left.fwd.low@small` は
  その立ち方でなければ踏み、そうであれば動かない (サンプルを書いて分かった。これがないと構えるたびに足を踏み直す)。
- 定義した名前は、段の中で語として書ける。**長さを書かなければ定義どおりの長さ** (`pose` は 1 拍)。
  **書けば全体をその長さに伸び縮みさせる** (`jab:1/2`)。
- `jab@mirror` は左右を入れ替えて行う。
- 引数は持たせない。繰り返しの一部だけを変えたいときは、共通の部分を `move` にして、違う部分を並べて書く
  (繰り返しに別の終わりを付ける構文は足さない)。

**段の重なり。** 段は包含の木になる: `body` ⊃ {`steps`, `arms` ⊃ {`leftArm`, `rightArm`}, `leftLeg`, `rightLeg`, `torso`, `head`}。

- `body` は新しい段で、全身を受け持つ。
- **定義した語を段に書くと、その語のうち、その段が受け持つ部位のぶんだけを行う。** `body { guard }` は全身、
  `leftArm { guard }` は構えの左腕だけ。その段に当たる部位が 1 つもなければエラー。
  (はじめは「使う部位をすべて含む段にだけ書ける」としていたが、`jab` の戻りを `guard` と書けず、
  構えの腕の形を 2 か所に書くことになった。)
- 同じ部位に 2 つの段が語を書いたら、狭い段が勝つ。狭い段が `skip` の間と、終わった後は、広い段に従う。
  誰も語を書いていない部位はそのまま (今の「書かない段は前のまま」と同じ)。`hold` は「止まる」と言っているので広い段を遮る。
- 今の「`arms` と `leftArm` は同じフレーズに書けない」という規則はなくなる。

**1 つの段の中で動きを重ねる** (ユーザーの案、2026-11-14。Lily# の `voice { } { }` にあたるもの)。
記法は `{ … } & { … }` に決定。`voice` という語はユーザーが避けた。

```shosa
body { guard:0 | { jab:1/2 jab:1/2 cross:1 } & { stepIn:2 }  frontKick@mirror:2 | hold:4 }   // 勧め: & でつなぐ
body { guard:0 | { jab:1/2 jab:1/2 cross:1 } { stepIn:2 }  frontKick@mirror:2 | hold:4 }     // 並べるだけ
```

| 記法 | 良い点 | 困る点 |
|---|---|---|
| `{ … } & { … }` (勧め) | 同時であることが記号で見える。続けて 2 組書ける。**波括弧は必ず書く**: 重ねる単位は波括弧の中の列で、1 語でも `{ walk:4 } & { wave:4 }`。括弧を省けるとした前の案は、`a b & c d` で何が重なるのか読めず、連続する動きを単位にできないように見えた (ユーザーの指摘) ので取り下げ | 記号が 1 つ増える |
| `{ … } { … }` | 最も軽い | 波括弧の並びは「順に行う 2 つのかたまり」にも読める。2 組を続けて書くと 4 列の 1 組と区別できない |
| `voice { … } { … }` | Lily# と同じ | 動きに「声部」は合わない (ユーザー) |

意味はどの記法でも同じ:

- 列はどれも同じ時刻に始まる。列に書けるのは、その段に書けるものと同じ。
- 長さは最も長い列の長さ。短い列は、終わった後は何も言わない (`skip` と同じ)。
- **同じ部位に 2 つの列が書いたら、後ろの列が勝つ。** 前の列が土台、後ろの列が上書き。
  `{ walk:4 } & { wave:4 }` は歩きながら右腕だけ振る (`walk` の右腕の振りは `wave` に譲る)。
  混ぜる (2 つの動きの中間を取る) ことはしない。部位ごとに、どちらか一方。
- 段との使い分け: 段は `section` の端から端まで続く並行 (Lily# のパートや譜表)、これはその場かぎりの並行。
  これがないと、連携の途中で足を 1 回動かすだけのために `steps` の段を開いて `skip` で位置を合わせることになる。
- 重なりの規則は 1 つにまとまる: **より狭く、より後ろに書いたものが勝つ** (狭い段 > 広い段、後ろの列 > 前の列)。

### 12.4 `figure` と `dancer`

```shosa
figure lead
figure chorus
dancer alice humanoid on lead   at 0 1
dancer bob   humanoid on chorus at -1.5 0
dancer carol humanoid on chorus at 1.5 0  mirror
dancer dave  humanoid on chorus at 0 -1   delay 2  in Chorus
```

- `figure` は名前だけ。`rig` `at` `facing` は `dancer` に移す (体と立ち位置は踊り手のもの)。
  書式: `dancer 名前 体 on figure [at X Z] [facing …] [mirror] [delay 拍] [free] [in section …]`。
  `figure` のないファイルでは `on figure` を書かない (`dancer mage humanoid free`)。
- `dancer` のない `figure` は、既定の体で、原点に正面を向いて踊る。
- **`figure` を 1 つも書かないファイルは、名前のない 1 体を持つ。** 段を `section` の直下に書く
  (`section Idle { body { … } }`)。`figure` を書いたファイルでは、段は必ず `figure` のブロックの中。混ぜない。
  ゲームの 1 キャラクターのファイルから入れ子が 1 段減る。

### 12.5 クリップ、ループ、その場の動き

- **`form` のないファイルでは、`section` の 1 つずつが独立したクリップ**になる (どれも中立の姿勢から始まる)。
  `form` があれば、`score` が指す `form` がクリップ (名前のない `form` がファイルの既定。`score` は 12.8)。
  glTF は 1 ファイルにクリップの数だけアニメーションを持つ。BVH と `.vrma` はクリップごとに別のファイル。
- **`section 名前 loop`** = 終わりが始まりにつながる。求解器は「自分自身の後に続いている」として解く
  (始まりの状態 = 終わりの状態から移動ぶんを引いたもの)。だから歩行のループに開始姿勢を書かなくてよい。
  向きが 1 周で元に戻らないなど、つながらないときは診断を出す。
- **`section 名前 inplace`** = 書き方は変えず (`left.fwd` のまま)、出力から床の上の移動 (等速ぶん) を除く。
  除いた速さ (m/s) を出力に添え、エンジン側が移動を持てるようにする。左右の揺れと上下は残す。

### 12.6 イベントの印

- **`!名前`** をイベントの末尾に付ける (`fwd:1@sharp!hit`)。その部位が目標に**着いた瞬間**に立つ
  (`@sharp` なら前半の終わり)。`@` は言語の語、`!` は書き手が付ける名前、と記号で分ける。
- 出力: glTF は `extras`、ほかは横に置く JSON (`名前.events.json`) に、クリップ・時刻・印の名前を書く。

### 12.7 足した語 (文法の骨組みに触れるもの)

| 不足 | 書き方 |
|---|---|
| 物理を無視する | `@free` (イベント)、`dancer … free` (ずっと)。外れるのは力学の規則と診断で、骨の長さは外れない (11 節) |
| ステップ・跳躍しながら回る | `left.fwd@turn(left.quarter)`、`jump@turn(right.half)`。引数は丸括弧 (Lily# と同じ) |
| 45 度刻み以外の角度 | 高さの語の位置に数 (水平からの度): `fwd.30`、`fwd.-70`。`high` = 45、`low` = -45 |
| 自分の体との接触 | 腕の場所を足す: `chin`、`belly`、`across.shoulder` (反対の肩)、`clap` (`arms` で両手を合わせる) |
| 相手との接触、視線、向き | `figure名.場所` を目標にする: `rightArm { b.hand }`、`head { b.head }`、`steps { turn.b }` |
| 床から浮く、二段ジャンプ | `steps { lift(0.4) }` = 足が床から 0.4 m の高さにいる。`lift.fwd(0.4)` は `jump` と同じ語で移動も書く。`land` で床に戻る。`@free` か `dancer … free` のときだけ書ける (物理に従う跳躍は `jump`)。二段ジャンプは `lift(0.4):0.3s@free lift(0.9):0.3s@free land:0.4s@free` |
| 足を動かさずに体重を移す | `steps { shift.left }` `shift.right` `shift.center`。待機の基本なのに語がなかった (サンプルを書いて分かった) |

`repeat N { … | }` は中に小節線を書ける (今のサンプルは小節ごとに `repeat` を書き分けている)。

相手を目標にできるのは、その `figure` を踊る `dancer` が 1 人のときだけ (何人もいれば、どの体か決まらないのでエラー)。

### 12.8 曲を参照する

ユーザーの方針 (2026-11-14): `.shosa` の側で上書きでき、別の `form` も定義できること。Lily# の `score` との関係を決めること。
(はじめの案「曲を参照したら `tempo` `time` `form` はエラー」は退けた。)

Lily# では、出力の単位は `score`。`score 名前 { form F  staff … }` が「どのパートを、どの順で」を決め、
`lysc midi --score 名前` が `song-名前.mid` を書く。名前のない `score` と `form` がファイルの既定。

案:

```shosa
music "song.lys"                  // 曲の既定の score。鳴るパートと並べる順はそこから来る
music "song.lys" score practice   // 名前の付いた score
tempo 96                          // 上書き: このテンポで踊り、音もこのテンポで鳴る
form { Verse Chorus Chorus }      // 上書き: この順で踊り、音もこの順で鳴る
form short { Chorus }             // 別のクリップ。音は Chorus だけ
```

- **`music` が指すのは Lily# の `score`**。鳴るパートを決めているのが `score` なので、`form` ではなく `score` を指す。
- **書かなければ曲から来て、書けば上書き**。`form` がなければ、順はその `score` の `form`。`tempo` がなければ曲のテンポ。
- `form` に書けるのは曲にあるセクションの名前。曲にないセクションはエラー (鳴らす音がない)。
- **`time` は上書きできない** (エラー)。音符の小節の区切りは曲の側で決まっていて、変えようがない。
- **Shosa にも `score` を置く** (ユーザーの案、2026-11-14: `.shosa` の側でも複数の `score` を切り替えて使えると便利)。
  はじめの勧めは「足さない (出力の単位は `form` で足りる)」だったが、退けた。下の「`score`」。

**`score`: 出力の単位。** Lily# と同じ形で、「どの順を、誰が、どの音で」を 1 つにまとめる。

```shosa
music "song.lys"
form short { Chorus }

score { }                                         // 既定: 曲の順、全員。書かなくても同じ
score practice { form short  tempo 80 }           // 練習用: サビだけ、遅く
score solo     { dancer alice }                   // alice だけ
score karaoke  { music "song.lys" score karaoke } // 曲の別の score の音で
```

- 中に書けるもの: `form 名前` (どの順)、`dancer 名前 …` (誰が出るか。書かなければ全員)、`music …`、`tempo N`、`title`。
  どれも、書かなければファイル直下の値。直下の `tempo` `music` と名前のない `form` は「ファイルの既定」になる。
- 名前のない `score` はファイルの既定で、書かなくてもある。出力は入力と同じ名前、`score 名前` は `入力-名前`。
  CLI は `--score 名前`、プレビューは `score` を切り替えられる (Lily# と同じ)。
- 名前の付いた `form` は、`score` から指されて使われる (Lily# と同じ)。
- 1 つの `score` が出すクリップ: `form` があればその 1 本。`form` がどこにもなければ `section` ごとに 1 本 (12.5)。
- Lily# からの受け取り方は下の「Lily# の口」。順とテンポの上書きは、Lily# を変えなくても実現できる見込み。

**Lily# の口** (2026-11-14 にコードを読んで調べた。ビルドも実行もしていない。`C:\MyProj\LilySharp`、版 0.16.0):

- **`lysc` に時刻表を書き出すコマンドはない。** JSON を出すのは `boxes` と `review --json` だけで、時刻を持たない。
  だから `lysc` を呼ぶ形ではなく、**`LilySharp.Core` をライブラリとして参照する** (net10.0。nuget.org にあるかは未確認なので、
  プロジェクト参照かローカルの `.nupkg`)。
- **ライセンスは GPLv3 以降。** リンクすると Shosa の配布条件に効く。ライセンスの決定 (第 4 段階) の前に考える。
  避けるなら、音楽の連携だけを別の実行ファイルに分ける手がある。
- 読み込み: `SyntaxTree.Parse(text)`。`using` の展開 (`UsingExpander`) と `singer` の展開 (`Editing.SingerParts`) は別の呼び出し。
  手本は CLI の `LoadAndParse` (`LilySharp.Cli/Program.cs` の 1360 行あたり)。
- `score` を探す: `RenderSpecParser.FindByName(tree, name)` / `FindAll(tree)` が `RenderSpec` (`Name`、`Form`) を返す。
- MIDI: `new MidiExporter { Form = spec.Form, Score = spec }.Export(tree)` が `MidiFile` を返す。そこから:
  - `SectionStarts` (`SortedDictionary<int, string>`): 繰り返しと飛び越しを展開した演奏順で、セクションの開始ティックと名前。
    長さは次の開始との差、最後は `EndTick` まで。同じティックに 2 つ始まると上書きされるおそれがある (未確認)。
  - `BarTicks`: 小節線のティック。弱起は最初の小節線から推し量る (専用の値はない)。
  - `Tracks[0].TempoChanges` (`Tick`, `MicrosecondsPerBeat`) と `TimeSignatures` (`Tick`, `Numerator`, `Denominator`)。
  - 秒への変換: `MidiClock.SecondsOf(midi)`。
- 音: `WavRenderer.Render(midi, soundFontPath, output)` が手元の `MidiFile` から WAV を書く (MeltySynth。`.sf2` が要り、同梱はない)。
- **順の上書き**: 外から順を渡す口はない (`MidiExporter.Form` は同じ木の中の `form` の節しか受けない)。
  Lily# を変えない手は、読む前のテキストの末尾に `form ShosaX { … }` と `score ShosaX { form ShosaX … }` を足してから解析すること。
  Lily# を変えるなら、`MidiExporter` に演奏順のリストを受ける口を足す (`PlayForm` のあたり)。
- **テンポの上書き**: 口はないが、書き出した `MidiFile` の `Tracks[0].TempoChanges` を書き換えれば済む。ティックは変わらないので
  `SectionStarts` も `BarTicks` もそのまま使え、WAV もそのテンポで鳴る。曲の途中にテンポ変化があるときは、
  置き換えではなく比で縮める (`tempo 96` は「最初のテンポを 96 にする比を全体に掛ける」)。
- `section` は名前で曲のセクションに対応する。振付のほうが短ければ残りは止まる (段の長さの規則と同じ)。
  長ければエラー。同じ名前のない曲のセクションでは止まったまま。
- 途中のテンポ変化と弱起は曲から来る。Lily# からの受け取り方が未調査なので、ここは仮 (11 節)。

### 12.11 サンプルを書いて分かったこと (第 2 段階の 2)

今のサンプル 9 本と、ゲーム向け 3 本 (`fighter` `npc` `mage`。クリップ 15 個)、曲に合わせた群舞 1 本を書いた。

**設計に戻して直したもの** (上の各節に反映済み):

- `pose` の `steps` は立ち方として読む (12.3)。
- 定義した語は、書いた段が受け持つぶんだけ行う (12.3)。
- 先頭の `:0` はほかのイベントより先に効く。`loop` には要らない (12.2)。
- `figure` のないファイルの `dancer` は `on` を書かない (12.4)。
- 体重だけを移す `shift`、小節線を含む `repeat` (12.7)。

**書きやすかったところ**:

- ゲームのキャラクター 1 体が 1 ファイルに収まり、構え (`guard`) を 1 か所に書いて全部のクリップで使える。
- `kick | kick@mirror`、`grapevine | grapevine@mirror` で、左右を入れ替えた複製が消えた。
- 被弾や身振りは秒で書くほうが自然で、拍と混ぜても困らなかった。
- 数の角度は、腕振り (`fwd.-70`)、うなずき (`fwd.-25`)、のけぞり (`back.70`) で毎回使った。45 度刻みでは書けない動きが多い。

- 床から浮く・二段ジャンプが書けなかった。`free` は規則を外すだけで、体を床から上げる語がなかった。
  高さの目標 `lift(高さ)` と `land` を足した (12.7。ユーザーが入れると決めた)。

**残っている穴**。「手」の列の勧めのとおりに進める (ユーザー: 提案どおりで良い):

| 穴 | 内容 | 手 |
|---|---|---|
| 体幹の数の角度の読み | 数は水平からの度なので、`torso { fwd.60 }` は 30 度の礼。60 度の礼に見える | 規則は 1 つのままにして文法書に明記する (勧め)。体幹だけ直立からの度にする案は、規則が 2 つになる |
| `form` を書き忘れた振付 | `form` がなければ `section` ごとに別のクリップで、どれも中立から始まる。続けて踊るつもりの 2 つが切れる (`taiso`) | `section` が 2 つ以上あって `form` も `loop` もないとき、情報の診断を出す |
| クリップごとの `guard:0` | `fighter` では 4 つのクリップが `body { guard:0 … }` で始まる | このまま (その場に書いてあるほうが読める)。ファイル全体の開始姿勢 `start guard` を足す案もある |
| 定義の長さを覚えていないと書けない | 長さを書かない `jab` は定義どおり 2 拍。小節を数えるには定義を見る必要がある | 書き手は長さを書く。ホバーに定義の長さを出す。小節線の検査が間違いを拾う |
| `inplace` と回転 | 除くのは移動だけ。その場で向きを変えるクリップの回転をどちらが持つかは決めていない | 回転は残す (勧め) |
| 足を出して進む動きの数え方 | 足は支持足からの相対なので、構え (左が小さく前) から `left.fwd@small` と書いても同じ場所を踏み直すだけで進まない。進むには `left.fwd` (大きく) の後に `right.back@small` (詰める)。下書きで一度間違えた | 文法書に例を書く。進まない一歩に情報の診断を出す案もある |
| 走る | `steps` は片足が必ず床にある。両足が離れる走りは書けない | 定番の動きでは勝負しない (ROADMAP 1 節) ので後回し |

手首・指・肩・体幹のひねり・座る・寝るは、今の文法と同じく書けない (招く手つき、肩をすくめる、倒れる)。
求解器と骨格の側の話で、文法の骨組みは変えない。
