# Shosa (所作) 設計メモ

動きをテキストで書き、コンパイルして人形の動きにする言語の試作。拡張子は `.shosa`。
Lily# が楽譜に対してしていることを、身体の動きに対して行う。

名前は「所作」から。能では舞を分けた動きの最小単位をこう呼び、型付 (舞の記譜) に従って並べる。

**いまの文法の骨組みは 26 節** (`figure` `dancer` `form` `score` は省略できない。1 つの `score` が 1 つの書き出しファイル)。それより前の節の例は、その前の形で書いてある。

## 1. パイプライン

```
text ──▶ SyntaxTree ──▶ MotionIr ──▶ MotionClip ──▶ PNG / HTML / JSON / BVH
        (Syntax/)      (Semantics/)  (Motion/)      (Output/)
         SH0xxx          SH1xxx        SH2xxx
```

各段は前段から作られる不変の値で、`ShosaCompilation` が一か所でつなぐ。診断は層ごとに番号帯を分ける。

| 段 | 役割 | Lily# での対応 |
|---|---|---|
| SyntaxTree | 損失のない構文木。語彙を知らない | Parser / Syntax |
| MotionIr | 「どの部位が、いつ、どこへ」。JSON になる | Semantics / Music |
| MotionClip | 全フレームの全関節位置と、同じ姿勢を表す全骨の回転 (9 節) | Svg / Rendering (浄書) |

## 2. 言語サーバーと Roslyn を前提にした決定

1. **赤緑木**。緑ノードは位置を持たず不変、赤ノードは位置つきの遅延ビュー (`Green.cs`, `SyntaxNode.cs`)。
   空白とコメントはトークンのトリビアに入り、`ToFullString()` は常に元のテキストと一致する。
2. **パーサーは例外を投げず、トークンを捨てない**。足りないものは幅 0 の欠落トークン、
   置けないものは `Error` ノードになる。打ちかけのファイルにも木がある。
   - 閉じ忘れたトラックは次の `名前 {` で打ち切る (次のトラックを巻き込まない)。
   - 行末の `.` は次の行の語を取らない (補完が次の語を出す位置)。
3. **文法は語彙を知らない**。`left.fwd` も `turn.left.quarter` も構文上は「`.` でつないだ語」。
   意味はバインダーが `Vocabulary.cs` の表で決める。語を足しても文法は変わらず、
   補完・ホバー・AI 向け文法書は同じ表から生成できる。
4. **字句解析は行をまたぐ状態を持たない** (コメントも文字列も行末で終わる)。
   これが差分再パースの健全性の根拠になっている。
5. **差分再パース** (`SyntaxTree.WithChange`)。最上位の項目 (ヘッダー行、figure、phrase、form) 単位で
   緑ノードをそのまま引き継ぐ。再利用の条件は「診断がなく、改行で終わる」こと。
   乱数編集で全文パースとの一致を試験している (`SyntaxTests`)。
6. **ソース位置は最後まで運ぶ**。IR の各セグメントと Clip の `Spans` が元の語の範囲を持つ。
   プレビューで演じている語が光り、語をクリックするとその時刻へ飛ぶ。
7. **診断は範囲・番号・直し方を持つ**。`SH1011` (腕に `left` と書いた) は書くべき語を示すので、
   そのままクイックフィックスになる。

未着手で、設計上の置き場所だけ決めてあるもの:

- **型つき構文ノード**。今は汎用の `SyntaxNode` 一種類。文法が固まったら、Roslyn の `Syntax.xml` と同じく
  宣言から緑・赤のクラスを生成する (Roslyn のソースジェネレーターを使う箇所)。
- **求解の差分化**。フレーズは「入口の状態 (足の位置・向き・各部位の姿勢) → 出口の状態」の関数にできる。
  緑ノードの同一性と入口の状態をキーにキャッシュすれば、編集したフレーズ以降だけ解き直せる。
  今の `FigureSolver` は全体を一度に解く。
- **言語サーバーの残り**。ホバーの小さな姿勢図、セマンティックトークン、コードレンズ (フレーズを再生)、
  クイックフィックス (`SH1011` の語の置き換えなど)。できている部分は 8 節。

## 3. 言語

```
title "Walk"
tempo 100
time 4/4

figure a "Walker" { rig humanoid }

phrase Walk {
  a {
    steps { left.fwd right.fwd left.fwd right.fwd | left.fwd right.fwd left.fwd together }
    arms  { side:2 down:2 | hold:4 }
  }
}

form { Walk }
```

- **トラック** = 身体の部位ごとの列。ラバノーテーションの譜表の列に当たる。
  `steps` (体重と足)、`arms` `leftArm` `rightArm`、`leftLeg` `rightLeg` (体重のない脚)、`torso`、`head`。
- **イベント** = `目標[:拍数][@様態]`。目標には、その長さの**終わり**に到達する。長さの既定は 1 拍。
- **目標** = 方向の語を `.` でつなぐ。方向 (`fwd` `back` `side` `across`、体幹は `left` `right`) と
  高さ (`low` `mid` `high`)、単独の `up` `down`。腕は身体の場所 (`hip` `chest` `shoulder` `head`) も取れる。
- **`side` / `across`**。腕と脚は左右でなく「正中線から離れる / 越える」で書く。
  だから `arms { side }` の一語が両腕に正しい。
- **足** = `足.方向`。位置はもう一方の足 (支持足) からの相対。`together`、`turn.left.quarter`、
  `jump.apart`、`both.low` (膝を曲げる)。
- **`|`** は小節線。拍数が合わなければ `SH1002`。
- **`repeat N { }`**、`form { A B*2 }`。

## 4. 手順 1 (実装なしでサンプルを書く) で分かったこと

- **半円は中間点を書く必要がある**。`down` から `up` は正反対で、前回りか横回りかが決まらない。
  記譜の世界でも中間の方向を書く。黙って選ばず `SH2001` で指摘する。
- **ボックスステップは「前・横・閉じる」**。足を支持足からの相対にしたので、踊り手の言い方のまま書ける。
  絶対座標や「前斜め」にすると書き方が割れる。
- **お辞儀は体幹を一本の肢として書ける**。`torso { fwd.high }` で 45 度。専用の語は要らなかった。
- **頭だけは体幹に相対**。お辞儀で顔が前を向いたままになるのを避けるため。腕と体幹は重力基準。
- **決めきれていない点**: 歩くときの自然な腕振り (書かせるか、様式として自動で足すか)、
  手拍子など部位どうしの接触、二人の接触、視線の対象 (`look at b`)、反対側で繰り返す `mirror { }`。

## 5. 求解器 (今の版)

物理も学習モデルも使わない。閉じた式の曲線と 2 関節の逆運動学だけ。

- 足: 着地点は支持足からの相対で決まり、遊脚は弧を描く。接地中の足は動かない (試験あり)。
- 体重: 着地の瞬間ごとに「両足の間、新しい足寄り」を鍵にし、形状保存の 3 次補間で結ぶ。
  歩行では骨盤が等速で進み、左右に揺れる。片脚を上げている間は支持足の上へ寄る。
- 高さ: 両足に脚が届く範囲で最も高く。大股なら自然に沈む。
- 跳躍: 滞空時間から高さが決まる (h = gT²/8)。テンポを上げれば低くなる。
- 検査: `SH2002` 脚が届かない、`SH2003` 速すぎる、`SH2004` 両足が床を離れる。

これは「語彙が見られる動きに解けるか」を確かめる版。質を上げる段では、この位置に
学習済みのモーションモデルを「演奏者」として差し込む (Lily# の DiffSinger と同じ位置づけ)。
IR が境界なので、言語側は変えずに済む。

## 6. 確かめ方

```
dotnet test Shosa.slnx
dotnet run --project Shosa.Cli -- sheet   samples/walk.shosa -o out/walk.png    # 連続写真と床の俯瞰
dotnet run --project Shosa.Cli -- preview samples/walk.shosa -o out/walk.html   # ソースと連動する 3D
dotnet run --project Shosa.Cli -- ir      samples/walk.shosa                    # 中間表現
```

`sheet` は `--step 0.5 --from 8 --to 16` で間隔と範囲を選べる。
`shosa grammar -o docs/GRAMMAR_FOR_LLM.md` は AI 向けの文法書を語彙表から作り直す (試験が一致を見張る)。

## 7. 手順 6 (AI に書かせる試験) の結果

文法書だけを読ませた 2 体に、振付 3 本と局所修正 1 件ずつを書かせた (`trials/A`, `trials/B`)。
8 ファイルすべてが診断なしでコンパイルでき、出た診断は警告 1 件 (`SH2003`) だけだった。

直したもの:

| 見つかったこと | 対処 |
|---|---|
| `.high` の次の、高さを書かない一歩がつま先立ちのままだった | 高さを書かない一歩は普通の高さに着く |
| つま先立ちの足が足跡に描かれなかった | 足跡はつま先が床にあるかで判定 |
| `@sharp` が最初から全速で、拍の直後のコマですでに動いていた | 前半で着いて止まる、両端をなめらかに。最高速度は半分 |
| 連続写真が拍ちょうどでなく最寄りのフレームを写していた | フレーム間を補間して拍ちょうどを写す |
| `back` が 0.4 m で、文法書の「一歩」(0.5 m) と違った | `fwd` と同じ 0.5 m。前 2 歩・後ろ 2 歩で元に戻る |
| 後ろ交差の語がなく、`back.across` が一歩ぶん後ろへ下がった | `back.across` は支持足のすぐ後ろ (0.12 m) |
| `together` に高さを書けなかった | `together.high` など |
| 横曲げで腕が垂直のまま残る (部屋基準)。腕 2 本を別々に三角法で書いていた | `@body` で体幹基準にできる。既定は部屋基準のまま |
| 半拍の動きが 1 拍おきの連続写真に写らず、確認用の一時ファイルを作っていた | `--step` `--from` `--to`。文法書に間隔の規則を明記 |
| 肩の線が腕の色で、曲がった上腕に見えた | 体幹の色にした |
| 文法書の不足: figure の書き方の例、片脚立ちの体重の規則、膝上げの書き方 | 追記 |

腕の既定を体幹基準に変える案は採らなかった。前屈で「腕を垂らす」が `fwd` になってしまうため。
記譜の慣習 (部屋基準が標準、身体基準は指定したとき) と同じにした。

残っている不足 (語彙の設計が要る):

- **ステップしながらの回転**。回るワルツは、回転を半拍に押し込むしかなかった。
- **接触**。手拍子、握手、相手の肩に手。
- **繰り返しの一部だけ変える**。`Combo*2` の 2 回目だけ変えるには、フレーズを複製するしかない。
- **開始姿勢**。最初の構えに 1 拍以上かかる。
- **腕の目標の不足**。あご (ガード)、身体の前で両手を合わせる、肘の向き。
- **体幹の角度が 45 度刻み**。60 度の礼が書けない。
- **図どうしの関係**。「相手に向かって」は座標で書くしかない。

## 8. エディター (手順 7)

```
VS Code ──(LSP, 標準入出力)── Shosa.Lsp ── Shosa.Core
   │                              │
   │                              └─ shosa/clip 通知: 編集のたびに解いた動きを送る
   └─ webview (dist/preview.js): 動きを描くだけ。構文は知らない
```

- **`Shosa.Lsp`**。`LanguageServer` は「メッセージを受けて、コールバックで返す」だけのオブジェクトで、
  入出力は `Program.cs` が受け持つ。試験はオブジェクトに直接話しかける。
  - 編集は範囲で届き、`SyntaxTree.WithChange` に渡す (触っていないフレーズは再パースしない)。
  - 補完とホバーは同じ関数 (`Words.ForTarget`) を引く。その場所に来られる語は語彙表から決まる。
    `left.` の後には足の方向と高さ、`arms { side.` の後には `across` (逆向き) を除いた語が出る。
  - ホバーは語の意味に加えて「何小節目の何拍目から、何拍かけて」を出す (IR がソース位置を持つため)。
- **`editors/vscode`**。拡張本体 (`src/extension.ts`) は薄い。サーバーを起こし、プレビューを開き、
  3 種類のメッセージを運ぶだけ。
  - サーバー → プレビュー: 解いた動き (編集のたび)。見ている時刻は保つので、語を直すとその姿勢が変わる。
  - エディター → プレビュー: カーソル位置。その語の**終わり**の時刻へ移る (語が指す姿勢がそこにある)。
  - プレビュー → エディター: 演じている語 (ハイライト)、クリックした肢の語 (そこへ飛ぶ)。
- 開発時は F5 (`.vscode/launch.json`)。サーバーは `Shosa.Lsp/bin/Debug` のものを使う。
  配布時は拡張の `server/` に置く (未着手)。

連続写真は左が青、右が赤。鏡像の間違いが一目で分かる。動画を見られない書き手 (AI、試験) は
この 1 枚で動きを確かめる。

## 9. 回転つきの骨格と BVH (第 1 段階の 1 と 2)

```
shosa bvh samples/walk.shosa -o out/walk.bvh      # メートル。--scale 100 でセンチメートル
shosa bvh samples/duet.shosa -o out/duet.bvh      # 人形が複数なら duet.a.bvh, duet.b.bvh
```

求解器は関節の位置で考えたままにし、**位置から回転を読み取る段を後ろに足した**
(`Skeleton.Rotations`)。求解器の式も、位置を使う連続写真・プレビュー・試験も変えていない。

- **骨の表は 1 か所** (`Skeleton.Bones`)。17 本。名前は VRM の人型 (`hips` `spine` `chest` `neck` `head`
  `leftUpperArm` …) で、休止姿勢は +z を向いた T ポーズ、+x が人形の左。glTF と `.vrma` も同じ表から書く。
- **ねじれは曲がる面から決める**。位置だけでは、肢が自分の長さの軸まわりにどう回っているかが決まらない。
  肘・膝の曲がる面の法線を蝶番の軸とし、休止姿勢での蝶番の軸 (肘は左が -y、右が +y。膝は +x) に合わせる。
  前腕とすねの回転は、親に対して蝶番の軸まわりだけになる。まっすぐな肢は、求解器が曲げる向き
  (`Rig.ElbowPole` `Rig.KneePole`。求解器と共有) を使う。
- **`spine` は長さ 0 の骨**で、`hips` と同じ位置から始まる。求解器は骨盤の点を中心に体幹を傾け、
  股関節は水平のまま残す。`hips` は向き (ヨー) だけ、傾きは `spine` に入れると位置が正確に再現できる。
  `chest` と `neck` は回らない。
- **足**はつま先の方向を向き、左右には傾かない。求解器はかかとを上げると足を少し伸び縮みさせて描くが、
  骨は伸びないので、つま先は方向だけが一致する。
- **回転は `ClipFigure.Rotations`** (骨ごとの四元数、親に対する回転)。JSON には出さない
  (プレビューは位置で描き、編集のたびに送られるため)。
- **BVH**。チャンネルは `Zrotation Xrotation Yrotation`。ルートの `OFFSET` は 0 (位置チャンネルに
  足すかどうかが読み手で割れるため)。角度は前のフレームに近い値へ寄せ、360 度の折り返しをなくす。
  1 ファイルに 1 骨格なので、人形ごとに別のファイルにする。

試験 (`SkeletonTests`): 回転から順運動学で求めた関節が求解器の位置に 1 mm 以内で戻る。
BVH を形式の定義から書いた読み手で読んでも同じ。1 フレームで 45 度以上回る骨がない
(曲がる面を逆に読むと肢が半回転ねじれる。棒人形では見えず、メッシュで見える)。

Blender 5.3 で確かめた結果 (2026-11-14。`walk` `taiso` `kick`):

```
shosa clip samples\walk.shosa -o out\blender\walk.clip.json
blender -b --python tools\blender_check.py -- out\walk.bvh out\blender\walk.clip.json out\blender\walk [人形の番号] [フレーム...]
```

`tools/blender_check.py` は BVH を読み込み、全フレームで骨の位置を求解器の関節と比べ、
骨ごとに平たい箱を付けて数コマを描く (左が青、右が赤。箱が平たいのでねじれが見える)。

- 読み込みの既定 (Forward -Z、Up Y) のままで人形は立ち、Blender の正面 (-Y) を向く。
- 骨の位置は求解器と全フレームで 0.14 mm 以内 (BVH の小数 4 桁の丸めの範囲)。
- 長さ 0 の `hips` は、読み込みが上向き 0.1 m の骨にする。`spine` は同じ点から始まり、動きに影響はない。
- 膝は前へ、肘は後ろ・外へ曲がり、腰に手を当てる姿勢や蹴りでも肢のねじれは見当たらない。
- シーンの終了フレームは 250 のまま (読み込みは短い動きに合わせて縮めない)。
- Blender は相対パスの描画先をドライブの根から解決する。スクリプトは絶対パスに直している。

まだ見ていないのは、皮膚のあるメッシュ (VRoid など) に載せたとき。箱では手首・足首・肩の
ねじれによる皮膚の崩れは分からない。第 1 段階の 4 で見る。

開発時の注意: VS Code が言語サーバーを起こしていると `Shosa.Lsp\bin` がロックされ、
`dotnet build Shosa.slnx` が失敗する。`dotnet build Shosa.Tests -o <別の場所>` でビルドし、
`dotnet test <別の場所>\Shosa.Tests.dll` で試験できる。

## 10. glTF と VRM Animation (第 1 段階の 3 と 4)

```
shosa gltf samples/duet.shosa -o out/duet.glb     # 人形が複数でも 1 ファイル。-o x.gltf ならテキスト (データは埋め込み)
shosa vrma samples/walk.shosa -o out/walk.vrma    # 人形が複数なら duet.a.vrma, duet.b.vrma
```

どちらも `Gltf.cs` の同じ関数が書く。Shosa の座標 (メートル、y が上、右手系、人形は +z を向き +x が左) は
glTF と VRM 1.0 の座標そのものなので、骨盤の位置も四元数も変換せずに書く。

- **ノードは `Skeleton.Bones` の 17 本**。`translation` が休止姿勢での位置、回転はなし (T ポーズ)。
  アニメーションは 1 つで、`hips` の `translation` と全部の骨の `rotation` を毎フレーム持つ (`LINEAR`)。
  四元数は前のフレームと同じ符号の側に寄せる (4 つの数をそのまま混ぜる読み手のため)。
- **glTF にはスキンを付ける (メッシュはない)**。Blender はスキンが名指ししたノードだけを骨にし、
  スキンがないと空のオブジェクトの列になる (Godot も同じはずだが確かめていない)。逆バインド行列は休止位置を原点へ戻す平行移動だけ。
- **glTF は人形ごとに親ノードを 1 つ置く** (名前は人形の ID。骨のノードの後ろに並べる)。
  骨盤どうしが同じ親 (シーン直下) を持つと、Blender は 2 体を 1 つのアーマチュアにまとめてしまう。
- **`.vrma` は glb に `VRMC_vrm_animation` 拡張を足したもの**。`humanoid.humanBones` で 17 本の骨のノードを指す。
  1 ファイルに人型 1 体。スキンも親ノードも付けず、`hips` をシーン直下に置く。
- 末端 (頭、手、足) の先は glTF に書く場所がない。読み手が長さを決める。動きには影響しない。

試験 (`GltfTests`): 形式の定義から書いた読み手で glb を読み、順運動学で求めた関節が求解器の位置に

## 11. 表記の基本規則の案 (ユーザーとの議論、2026-11-14。未決定)

決まったものではない。語彙を足すとき (第 2 段階) の出発点として残す。

**基本の規則は 2 つ。**

- 動きを書くと、書いた音価で、その動きを始めから終わりまで行う。
- 休符を書くと、その間は動きが止まる。

今の `語:拍数` と `hold:拍数` がほぼこれにあたる。違いは、今の語が**着く先の姿勢** (`side.high`) で、
案の語が**始めから終わりまでの一連の動き** (「手を振る」「蹴る」) である点。両立できる:
一連の動きを「姿勢の列に名前を付けたもの」として定義し、書かれた音価に合わせて全体を伸び縮みさせる。
第 2 段階の「ポーズの定義」を、姿勢だけでなく動きにも広げる形になる。動きをどう定義するかは未決。

**この 2 つに添えるもの。**

| 点 | 内容 | 今の Shosa |
|---|---|---|
| 並行する段 | 足と腕が別のリズムで動く。1 本の列では書けない | `steps` `arms` `rightLeg` などの段。音楽の声部と同じ |
| 休符の意味 | 体に「何もない」はない。休符は「今の姿勢のまま止まる」とし、「自然な姿勢に戻る」は動きとして書く (片足を上げたままの休符が書ける) | `hold` が前者 |
| 動き方 | 始めと終わりと長さが同じでも、鋭く止めるか、なめらかに着くかで別の動きになる | `@sharp` `@smooth` `@linear` |
| 拍に合う瞬間 | 音符は鳴り始めが拍に合うが、踊りの決めは着いた瞬間が拍に合う | 着く瞬間が音価の終わり。音楽と合わせるときに意識して決める |

音価の規則で決まらないもの (語彙の側で持つ): 向き、移動、体重がどちらの足にあるか、相手や物との接触。

**物理に従うか無視するかを `@` で書く案。**

- 既定は物理に従う。無視するほうを `@` で書く (名前の候補: `@free` `@float`)。今の求解器がすでに
  物理に従う側で (跳躍の高さは滞空時間から決まる)、診断 (`SH2003` `SH2004`) が AI の書いたものを直す手がかりだから。
- 無視できるのは力学: 重力 (跳躍の高さと滞空時間の関係)、速さの限界、体重の支え。
  無視できないのは形: 骨の長さ (`SH2002`)。骨は伸びない。
- 範囲: 語に付ければその動きだけ。ずっと浮いている人形のために、`figure` の宣言にも書けるようにする。
- 使いみち: 二段ジャンプ、空中で止まる、スローモーション、浮く人形。ゲーム向けに効く。
- 今の求解器は物理を計算しておらず、数本の規則があるだけなので、無視は「その規則と診断を外して
  指定どおりに補間する」で済む。第 3 段階のモデルは人の動きから学んでいるので、物理に合わない指定を
  守らない可能性がある。無視する語はモデルに渡さず今の求解器で動かす、という切り分けが要りそう (未実験)。


**`figure` から踊り手を分ける案 (`dancer`)。** 方針として採る (ユーザー、2026-11-14)。

(下の「音楽に合わせる向き」)。

| 役割 | Lily# (`.lys`) | Shosa (`.shosa`) |

| 書かれた内容の持ち主 | `part lead { instrument alto }` | `figure a "Walker" { rig humanoid at 0 0 facing front }` |

状態: **決定 (ユーザー、2026-11-14)。** 12.10 の表のとおり。ユーザーが個別に決めたのは 2 (拍)、9 (上書きできる)、

**3 節から 8 節は設計し直す前の文法の記録**で、書き方の例は古い (`figure a { rig humanoid }`、`phrase`)。今の文法は 12 節と 13 節、全体は GRAMMAR_FOR_LLM.md。

### 12.1 全体の形

```
[music "song.lys"]  または  [tempo N] [time N/N] [fps N]
[figure 名前 "ラベル"] …             振付の持ち主。1 体だけなら書かない
[dancer 名前 体 on figure …] …       踊る体。書かなければ既定の体
pose 名前 { 段 { 目標 } … }          名前の付いた姿勢
move 名前 { 段 { イベント … } … }    名前の付いた動き
section 名前 [loop] [inplace] { … }  時間の 1 区切り (今の phrase)
[form [名前] { A B*2 }]              並べる順
[score [名前] { form … dancer … }]   出力の単位 (12.8)。書かなければ既定の 1 つ
```

Lily# と語をそろえる。時間の区切りは `section` (今の `phrase` を改名)、並べる順は `form`、
演じる者は `singer` / `dancer`。曲を参照したとき `section Verse` が両方のファイルで同じ時間を指す。

### 12.2 音価の規則

- **イベント = `語[:長さ][@様態…][!印]`**。動きは書いた長さの始めから終わりまで行い、**終わりに着く** (今と同じ)。
- **`hold`** = 今の姿勢のまま止まる (休符)。**`skip`** = この段は何も言わない (LilyPond の `s`。下の「段の重なり」で使う)。
- **長さの単位**。`:2` は拍、`:0.3s` は秒、`:12f` はフレーム (`fps`、既定 30)。秒とフレームはテンポで拍に直して
  小節線の検査に入る。Lily# の音価 (`4` = 4 分音符) は採らない。踊りは拍で数え、語に数字を直に付けると読みにくい。
- **`:0`** = 時間をかけずにその姿勢にいる。使えるのはクリップの先頭だけ。**開始姿勢**はこれで書く
  (`body { guard:0 jab … }`)。専用の構文は足さない。先頭の `:0` は、どの段のものも、長さのあるイベントより先に効く
  (`body { guard:0 }` と `torso { back.70:0.2s … }` を並べると、構えた形から体幹が動く)。
  `loop` の `section` には要らない (始まりの状態は終わりの状態なので、`body { guard:8 }` で構えたままになる)。
- 拍に合う瞬間は「着く瞬間」。1 拍目に決めたい動きは、その前の拍から書く。曲に合わせるときは
  セクションの弱起 (Lily# の `partial` にあたるもの) で前に出す。

### 12.3 姿勢と動きの定義

```shosa
pose guard {
  steps { left.fwd.low@small }
  arms  { fwd.high@bent }
}
move jab       { leftArm  { fwd:1@sharp!hit  guard:1 } }
move cross     { rightArm { fwd:1@sharp!hit  guard:1 } }
move frontKick { rightLeg { fwd.low:1@bent  fwd:1@sharp!hit  fwd.low:1@bent  down:1 } }
```

- `pose` は段ごとに目標 1 つ、長さなし。`move` は段ごとにイベントの列。
- **`pose` は形で、動きではない。** すでにその形なら何も動かない。`steps` の行は「その一歩を踏み終えた立ち方」
  (両足の位置関係、高さ、体重) と読む。段に直に書いた `left.fwd` は毎回踏み出すが、`guard` の中の `left.fwd.low@small` は
  その立ち方でなければ踏み、そうであれば動かない (サンプルを書いて分かった。これがないと構えるたびに足を踏み直す)。
- 定義した名前は、段の中で語として書ける。**長さを書かなければ定義どおりの長さ** (`pose` は 1 拍)。
  **書けば全体をその長さに伸び縮みさせる** (`jab:1/2`)。
- `jab@mirror` は左右を入れ替えて行う。
- 引数は持たせない。繰り返しの一部だけを変えたいときは、共通の部分を `move` にして、違う部分を並べて書く
  (繰り返しに別の終わりを付ける構文は足さない)。

**段の重なり。** 段は包含の木になる: `body` ⊃ {`steps`, `arms` ⊃ {`leftArm`, `rightArm`}, `leftLeg`, `rightLeg`, `torso`, `head`}。

- `body` は新しい段で、全身を受け持つ。
- **定義した語を段に書くと、その語のうち、その段が受け持つ部位のぶんだけを行う。** `body { guard }` は全身、
  `leftArm { guard }` は構えの左腕だけ。その段に当たる部位が 1 つもなければエラー。
  (はじめは「使う部位をすべて含む段にだけ書ける」としていたが、`jab` の戻りを `guard` と書けず、
  構えの腕の形を 2 か所に書くことになった。)
- 同じ部位に 2 つの段が語を書いたら、狭い段が勝つ。狭い段が `skip` の間と、終わった後は、広い段に従う。
  誰も語を書いていない部位はそのまま (今の「書かない段は前のまま」と同じ)。`hold` は「止まる」と言っているので広い段を遮る。
- 今の「`arms` と `leftArm` は同じフレーズに書けない」という規則はなくなる。

**1 つの段の中で動きを重ねる** (ユーザーの案、2026-11-14。Lily# の `voice { } { }` にあたるもの)。
記法は `{ … } & { … }` に決定。`voice` という語はユーザーが避けた。

```shosa
body { guard:0 | { jab:1/2 jab:1/2 cross:1 } & { stepIn:2 }  frontKick@mirror:2 | hold:4 }   // 勧め: & でつなぐ
body { guard:0 | { jab:1/2 jab:1/2 cross:1 } { stepIn:2 }  frontKick@mirror:2 | hold:4 }     // 並べるだけ
```

| 記法 | 良い点 | 困る点 |
|---|---|---|
| `{ … } & { … }` (勧め) | 同時であることが記号で見える。続けて 2 組書ける。**波括弧は必ず書く**: 重ねる単位は波括弧の中の列で、1 語でも `{ walk:4 } & { wave:4 }`。括弧を省けるとした前の案は、`a b & c d` で何が重なるのか読めず、連続する動きを単位にできないように見えた (ユーザーの指摘) ので取り下げ | 記号が 1 つ増える |
| `{ … } { … }` | 最も軽い | 波括弧の並びは「順に行う 2 つのかたまり」にも読める。2 組を続けて書くと 4 列の 1 組と区別できない |
| `voice { … } { … }` | Lily# と同じ | 動きに「声部」は合わない (ユーザー) |

意味はどの記法でも同じ:

- 列はどれも同じ時刻に始まる。列に書けるのは、その段に書けるものと同じ。
- 長さは最も長い列の長さ。短い列は、終わった後は何も言わない (`skip` と同じ)。
- **同じ部位に 2 つの列が書いたら、後ろの列が勝つ。** 前の列が土台、後ろの列が上書き。
  `{ walk:4 } & { wave:4 }` は歩きながら右腕だけ振る (`walk` の右腕の振りは `wave` に譲る)。
  混ぜる (2 つの動きの中間を取る) ことはしない。部位ごとに、どちらか一方。
- 段との使い分け: 段は `section` の端から端まで続く並行 (Lily# のパートや譜表)、これはその場かぎりの並行。
  これがないと、連携の途中で足を 1 回動かすだけのために `steps` の段を開いて `skip` で位置を合わせることになる。
- 重なりの規則は 1 つにまとまる: **より狭く、より後ろに書いたものが勝つ** (狭い段 > 広い段、後ろの列 > 前の列)。

### 12.4 `figure` と `dancer`

```shosa
figure lead
figure chorus
dancer alice humanoid on lead   at 0 1
dancer bob   humanoid on chorus at -1.5 0
dancer carol humanoid on chorus at 1.5 0  mirror
dancer dave  humanoid on chorus at 0 -1   delay 2  in Chorus
```

- `figure` は名前だけ。`rig` `at` `facing` は `dancer` に移す (体と立ち位置は踊り手のもの)。
  書式: `dancer 名前 体 on figure [at X Z] [facing …] [mirror] [delay 拍] [free] [in section …]`。
  `figure` のないファイルでは `on figure` を書かない (`dancer mage humanoid free`)。
- `dancer` のない `figure` は、既定の体で、原点に正面を向いて踊る。
- **`figure` を 1 つも書かないファイルは、名前のない 1 体を持つ。** 段を `section` の直下に書く
  (`section Idle { body { … } }`)。`figure` を書いたファイルでは、段は必ず `figure` のブロックの中。混ぜない。
  ゲームの 1 キャラクターのファイルから入れ子が 1 段減る。

### 12.5 クリップ、ループ、その場の動き

- **`form` のないファイルでは、`section` の 1 つずつが独立したクリップ**になる (どれも中立の姿勢から始まる)。
  `form` があれば、`score` が指す `form` がクリップ (名前のない `form` がファイルの既定。`score` は 12.8)。
  glTF は 1 ファイルにクリップの数だけアニメーションを持つ。BVH と `.vrma` はクリップごとに別のファイル。
- **`section 名前 loop`** = 終わりが始まりにつながる。求解器は「自分自身の後に続いている」として解く
  (始まりの状態 = 終わりの状態から移動ぶんを引いたもの)。だから歩行のループに開始姿勢を書かなくてよい。
  向きが 1 周で元に戻らないなど、つながらないときは診断を出す。
- **`section 名前 inplace`** = 書き方は変えず (`left.fwd` のまま)、出力から床の上の移動 (等速ぶん) を除く。
  除いた速さ (m/s) を出力に添え、エンジン側が移動を持てるようにする。左右の揺れと上下は残す。

### 12.6 イベントの印

- **`!名前`** をイベントの末尾に付ける (`fwd:1@sharp!hit`)。その部位が目標に**着いた瞬間**に立つ
  (`@sharp` なら前半の終わり)。`@` は言語の語、`!` は書き手が付ける名前、と記号で分ける。
- 出力: glTF は `extras`、ほかは横に置く JSON (`名前.events.json`) に、クリップ・時刻・印の名前を書く。

### 12.7 足した語 (文法の骨組みに触れるもの)

| 不足 | 書き方 |
|---|---|
| 物理を無視する | `@free` (イベント)、`dancer … free` (ずっと)。外れるのは力学の規則と診断で、骨の長さは外れない (11 節) |
| ステップ・跳躍しながら回る | `left.fwd@turn(left.quarter)`、`jump@turn(right.half)`。引数は丸括弧 (Lily# と同じ) |
| 45 度刻み以外の角度 | 高さの語の位置に数 (水平からの度): `fwd.30`、`fwd.-70`。`high` = 45、`low` = -45 |
| 自分の体との接触 | 腕の場所を足す: `chin`、`belly`、`across.shoulder` (反対の肩)、`clap` (`arms` で両手を合わせる) |
| 相手との接触、視線、向き | `figure名.場所` を目標にする: `rightArm { b.hand }`、`head { b.head }`、`steps { turn.b }` |
| 床から浮く、二段ジャンプ | `steps { lift(0.4) }` = 足が床から 0.4 m の高さにいる。`lift.fwd(0.4)` は `jump` と同じ語で移動も書く。`land` で床に戻る。`@free` か `dancer … free` のときだけ書ける (物理に従う跳躍は `jump`)。二段ジャンプは `lift(0.4):0.3s@free lift(0.9):0.3s@free land:0.4s@free` |
| 足を動かさずに体重を移す | `steps { shift.left }` `shift.right` `shift.center`。待機の基本なのに語がなかった (サンプルを書いて分かった) |

`repeat N { … | }` は中に小節線を書ける (今のサンプルは小節ごとに `repeat` を書き分けている)。

相手を目標にできるのは、その `figure` を踊る `dancer` が 1 人のときだけ (何人もいれば、どの体か決まらないのでエラー)。

### 12.8 曲を参照する

ユーザーの方針 (2026-11-14): `.shosa` の側で上書きでき、別の `form` も定義できること。Lily# の `score` との関係を決めること。
(はじめの案「曲を参照したら `tempo` `time` `form` はエラー」は退けた。)

Lily# では、出力の単位は `score`。`score 名前 { form F  staff … }` が「どのパートを、どの順で」を決め、
`lysc midi --score 名前` が `song-名前.mid` を書く。名前のない `score` と `form` がファイルの既定。

案:

```shosa
music "song.lys"                  // 曲の既定の score。鳴るパートと並べる順はそこから来る
music "song.lys" score practice   // 名前の付いた score
tempo 96                          // 上書き: このテンポで踊り、音もこのテンポで鳴る
form { Verse Chorus Chorus }      // 上書き: この順で踊り、音もこの順で鳴る
form short { Chorus }             // 別のクリップ。音は Chorus だけ
```

- **`music` が指すのは Lily# の `score`**。鳴るパートを決めているのが `score` なので、`form` ではなく `score` を指す。
- **書かなければ曲から来て、書けば上書き**。`form` がなければ、順はその `score` の `form`。`tempo` がなければ曲のテンポ。
- `form` に書けるのは曲にあるセクションの名前。曲にないセクションはエラー (鳴らす音がない)。
- **`time` は上書きできない** (エラー)。音符の小節の区切りは曲の側で決まっていて、変えようがない。
- **Shosa にも `score` を置く** (ユーザーの案、2026-11-14: `.shosa` の側でも複数の `score` を切り替えて使えると便利)。
  はじめの勧めは「足さない (出力の単位は `form` で足りる)」だったが、退けた。下の「`score`」。

**`score`: 出力の単位。** Lily# と同じ形で、「どの順を、誰が、どの音で」を 1 つにまとめる。

```shosa
music "song.lys"
form short { Chorus }

score { }                                         // 既定: 曲の順、全員。書かなくても同じ
score practice { form short  tempo 80 }           // 練習用: サビだけ、遅く
score solo     { dancer alice }                   // alice だけ
score karaoke  { music "song.lys" score karaoke } // 曲の別の score の音で
```

- 中に書けるもの: `form 名前` (どの順)、`dancer 名前 …` (誰が出るか。書かなければ全員)、`music …`、`tempo N`、`title`。
  どれも、書かなければファイル直下の値。直下の `tempo` `music` と名前のない `form` は「ファイルの既定」になる。
- 名前のない `score` はファイルの既定で、書かなくてもある。出力は入力と同じ名前、`score 名前` は `入力-名前`。
  CLI は `--score 名前`、プレビューは `score` を切り替えられる (Lily# と同じ)。
- 名前の付いた `form` は、`score` から指されて使われる (Lily# と同じ)。
- 1 つの `score` が出すクリップ: `form` があればその 1 本。`form` がどこにもなければ `section` ごとに 1 本 (12.5)。
- Lily# からの受け取り方は下の「Lily# の口」。順とテンポの上書きは、Lily# を変えなくても実現できる見込み。

**Lily# の口** (2026-11-14 にコードを読んで調べた。ビルドも実行もしていない。`C:\MyProj\LilySharp`、版 0.16.0):

- **`lysc` に時刻表を書き出すコマンドはない。** JSON を出すのは `boxes` と `review --json` だけで、時刻を持たない。
  だから `lysc` を呼ぶ形ではなく、**`LilySharp.Core` をライブラリとして参照する** (net10.0。nuget.org にあるかは未確認なので、
  プロジェクト参照かローカルの `.nupkg`)。
- **ライセンスは GPLv3 以降。** リンクすると Shosa の配布条件に効く。ライセンスの決定 (第 4 段階) の前に考える。
  避けるなら、音楽の連携だけを別の実行ファイルに分ける手がある。
- 読み込み: `SyntaxTree.Parse(text)`。`using` の展開 (`UsingExpander`) と `singer` の展開 (`Editing.SingerParts`) は別の呼び出し。
  手本は CLI の `LoadAndParse` (`LilySharp.Cli/Program.cs` の 1360 行あたり)。
- `score` を探す: `RenderSpecParser.FindByName(tree, name)` / `FindAll(tree)` が `RenderSpec` (`Name`、`Form`) を返す。
- MIDI: `new MidiExporter { Form = spec.Form, Score = spec }.Export(tree)` が `MidiFile` を返す。そこから:
  - `SectionStarts` (`SortedDictionary<int, string>`): 繰り返しと飛び越しを展開した演奏順で、セクションの開始ティックと名前。
    長さは次の開始との差、最後は `EndTick` まで。同じティックに 2 つ始まると上書きされるおそれがある (未確認)。
  - `BarTicks`: 小節線のティック。弱起は最初の小節線から推し量る (専用の値はない)。
  - `Tracks[0].TempoChanges` (`Tick`, `MicrosecondsPerBeat`) と `TimeSignatures` (`Tick`, `Numerator`, `Denominator`)。
  - 秒への変換: `MidiClock.SecondsOf(midi)`。
- 音: `WavRenderer.Render(midi, soundFontPath, output)` が手元の `MidiFile` から WAV を書く (MeltySynth。`.sf2` が要り、同梱はない)。
- **順の上書き**: 外から順を渡す口はない (`MidiExporter.Form` は同じ木の中の `form` の節しか受けない)。
  Lily# を変えない手は、読む前のテキストの末尾に `form ShosaX { … }` と `score ShosaX { form ShosaX … }` を足してから解析すること。
  Lily# を変えるなら、`MidiExporter` に演奏順のリストを受ける口を足す (`PlayForm` のあたり)。
- **テンポの上書き**: 口はないが、書き出した `MidiFile` の `Tracks[0].TempoChanges` を書き換えれば済む。ティックは変わらないので
  `SectionStarts` も `BarTicks` もそのまま使え、WAV もそのテンポで鳴る。曲の途中にテンポ変化があるときは、
  置き換えではなく比で縮める (`tempo 96` は「最初のテンポを 96 にする比を全体に掛ける」)。
- `section` は名前で曲のセクションに対応する。振付のほうが短ければ残りは止まる (段の長さの規則と同じ)。
  長ければエラー。同じ名前のない曲のセクションでは止まったまま。
- 途中のテンポ変化と弱起は曲から来る。Lily# からの受け取り方が未調査なので、ここは仮 (11 節)。

実装は 19 節。「ライブラリとして参照する」は、GPL と依存の重さから「別の実行ファイル `shosa-music` が参照し、JSON で渡す」になった。
弱起は受け取る。途中のテンポと拍子の変化にも踊りが付いていく (21 節。はじめは警告を出して最初のテンポで数えていた)。

### 12.11 サンプルを書いて分かったこと (第 2 段階の 2)

今のサンプル 9 本と、ゲーム向け 3 本 (`fighter` `npc` `mage`。クリップ 15 個)、曲に合わせた群舞 1 本を書いた。

**設計に戻して直したもの** (上の各節に反映済み):

- `pose` の `steps` は立ち方として読む (12.3)。
- 定義した語は、書いた段が受け持つぶんだけ行う (12.3)。
- 先頭の `:0` はほかのイベントより先に効く。`loop` には要らない (12.2)。
- `figure` のないファイルの `dancer` は `on` を書かない (12.4)。
- 体重だけを移す `shift`、小節線を含む `repeat` (12.7)。

**書きやすかったところ**:

- ゲームのキャラクター 1 体が 1 ファイルに収まり、構え (`guard`) を 1 か所に書いて全部のクリップで使える。
- `kick | kick@mirror`、`grapevine | grapevine@mirror` で、左右を入れ替えた複製が消えた。
- 被弾や身振りは秒で書くほうが自然で、拍と混ぜても困らなかった。
- 数の角度は、腕振り (`fwd.-70`)、うなずき (`fwd.-25`)、のけぞり (`back.70`) で毎回使った。45 度刻みでは書けない動きが多い。

- 床から浮く・二段ジャンプが書けなかった。`free` は規則を外すだけで、体を床から上げる語がなかった。
  高さの目標 `lift(高さ)` と `land` を足した (12.7。ユーザーが入れると決めた)。

**残っている穴**。「手」の列の勧めのとおりに進める (ユーザー: 提案どおりで良い):

| 穴 | 内容 | 手 |
|---|---|---|
| 体幹の数の角度の読み | 数は水平からの度なので、`torso { fwd.60 }` は 30 度の礼。60 度の礼に見える | 規則は 1 つのままにして文法書に明記する (勧め)。体幹だけ直立からの度にする案は、規則が 2 つになる |
| `form` を書き忘れた振付 | `form` がなければ `section` ごとに別のクリップで、どれも中立から始まる。続けて踊るつもりの 2 つが切れる (`taiso`) | `section` が 2 つ以上あって `form` も `loop` もないとき、情報の診断を出す |
| クリップごとの `guard:0` | `fighter` では 4 つのクリップが `body { guard:0 … }` で始まる | このまま (その場に書いてあるほうが読める)。ファイル全体の開始姿勢 `start guard` を足す案もある |
| 定義の長さを覚えていないと書けない | 長さを書かない `jab` は定義どおり 2 拍。小節を数えるには定義を見る必要がある | 書き手は長さを書く。ホバーに定義の長さを出す。小節線の検査が間違いを拾う |
| `inplace` と回転 | 除くのは移動だけ。その場で向きを変えるクリップの回転をどちらが持つかは決めていない | 回転は残す (勧め) |
| 足を出して進む動きの数え方 | 足は支持足からの相対なので、構え (左が小さく前) から `left.fwd@small` と書いても同じ場所を踏み直すだけで進まない。進むには `left.fwd` (大きく) の後に `right.back@small` (詰める)。下書きで一度間違えた | 文法書に例を書く。進まない一歩に情報の診断を出す案もある |
| 走る | `steps` は片足が必ず床にある。両足が離れる走りは書けない | 定番の動きでは勝負しない (ROADMAP 1 節) ので後回し |

手首・指・肩・体幹のひねり・座る・寝るは、今の文法と同じく書けない (招く手つき、肩をすくめる、倒れる)。
求解器と骨格の側の話で、文法の骨組みは変えない。


## 13. 設計し直した文法の実装 (第 2 段階の 3、2026-11-14)

12 節の文法を、字句から出力まで通して実装した。サンプル 13 本 (`samples/`) がすべてコンパイルでき、
`sheet` で動きを見て確かめた (`fighter` の待機・連携・歩行、`mage` の詠唱、`duet` の握手)。
ここには、12 節に書いていなくて実装のときに決めたことを残す。

### 13.1 パイプライン

```
text ──▶ SyntaxTree ──▶ ScoreIr ──▶ MotionClip (クリップごと) ──▶ PNG / HTML / JSON / BVH / glTF / VRMA
                        └ MotionIr (クリップごと)
```

- `Binder.Bind(tree, score)` は `ScoreIr` を返す。中身はクリップごとの `MotionIr`。`form` があれば 1 本、なければ `section` ごと。
- **`pose` `move`、段の重なり、`&`、`@mirror`、`dancer` の `mirror` `delay` `in` は、バインダーで消える。**
  `MotionIr` は「踊り手ごと、部位 (チャンネル) ごとに 1 列のセグメント」のまま。求解器は定義も重なりも知らない。
- `ShosaCompilation.Clips` がクリップの列、`Clip` はその先頭 (クリップのないファイルでは空のクリップ)。
- `MotionClip` の `Phrases` は `Sections` に改名。`Name` `Loop` `Inplace` `Marks`、`ClipFigure.Velocity` を足した。
  `ClipFigure` という名前は残っている (中身は踊り手)。

### 13.2 重なりの解き方 (バインダー)

- イベントはまず部位ごとに「生のイベント」として集め、最後に 1 列にする (`Resolve`)。
- 優先順位は数の列で、辞書順に比べる: `[段の狭さ, 段の番号, & の列の番号…, 定義の中の段の狭さ…]`。
  狭さは 部位の数 (8。15 節で高さを足した) − 受け持つ部位の数 (`body` 0、`arms` と `steps` 6、1 部位 7)。これで「狭い段が勝つ、後ろの列が勝つ」が 1 つの比較になる。
- **身振りの部位**: 時間を区切りごとに見て、その区間を覆うイベントのうち優先順位の高いものが勝つ。
  負けた区間のあとで広い段のイベントがまだ続いていれば、**残りの時間で、そのときの姿勢から、元の到着時刻に着く**
  セグメントになる (`arms { fwd:4 }` と `leftArm { skip:1 side:2 }` → 左腕は 0–1 前へ、1–3 横へ、3–4 で前に着く)。
- だからセグメントは「前のセグメントが着く前に始まる」ことがある。求解器は列をさかのぼって、
  「このセグメントが始まった瞬間に部位がいた場所」から補間する (`Chain`)。`hold` も列に残り、始まった瞬間の場所で止める。
- **足 (`steps`) は切れない**。優先順位の高いイベントと少しでも重なる一歩は、丸ごと落とす (診断は出さない。
  `body { guard:1 }` と `steps { stepIn:1 }` で構えの立ち方が落ちるのは意図どおり)。
- `skip` は何も出さない (時間だけ進める)。
- `:0` は長さ 0 のセグメントとして、その時刻のほかのセグメントより前に置く。使えるのはクリップの 0 拍目だけ (`SH1009`)。
  直後の小節線 (`guard:0 | …`) は 0 拍の小節として数えず、通す。`repeat 4 { … | }` の末尾の小節線も同じ。

### 13.3 定義の展開 (バインダー)

- 長さを書かない `move` の長さは、定義の中でいちばん長い段。書けば `書いた長さ ÷ 定義の長さ` で中の長さを全部掛ける
  (秒やフレームで書いた長さも一緒に伸び縮みする)。`pose` は 1 拍。
- 定義の中の段は、書かれた段が受け持つ部位との共通部分だけを行う。`@mirror` のときは、定義の段の部位を左右入れ替えてから共通部分を取る。
- 定義の中のセグメントのソース位置は、**`section` に書かれた語**の位置にする (プレビューで光るのも、`SH2xxx` が指すのも使った場所)。
  定義そのものの間違いは、使われていなくても定義の場所で一度検査する (`CheckDefinition`)。
- `pose` の `steps` から来た一歩には `Stance` の印が付く。求解器は「その足が、もう一方の足から見てすでにその位置 (2 cm 以内) なら踏まない」。
- 印 (`!名前`) の時刻はバインダーが決める: 音価の終わり、`@sharp` の身振りは半分、`jump` は 0.85 (着地)。定義を使った語に付けた印は終わり。
- 定義の名前に言語の語は使えない (`SH1005`)。自分自身を含む定義は `SH1017`。

### 13.4 求解器

- **ループ**: 足の段を 3 周ぶん空回しして立ち方を落ち着かせ、そこから「1 周前・この周・1 周後」の 3 周を記録して、まん中の 1 周だけを使う。
  身振りの列も同じく 3 周並べる。継ぎ目で動いている途中の足、体重の曲線の傾き、骨盤の高さのならしが、特別扱いなしでつながる。
  0 拍目に体重が踊り手の立ち位置に来るように全体をずらす。1 周で足の位置関係・高さ・向きが元に戻らなければ `SH2005` (警告)。
- **`inplace`**: 体重の最初から最後までの移動を、時間に比例して全関節から引く。引いた速さ (m/s) は `ClipFigure.Velocity`。回転は残す。
- **回りながらの一歩** (`left.fwd@turn(left.quarter)`): 支持足がその場で向きを変え、踏み出す足は**回り終わった向きで測った位置**に着く
  (「回ってから一歩」を 1 つの動きにしたもの)。回る前の向きで測ると、回った後に足が交差する。`jump@turn(…)` は空中で回り、回った向きで着地する。
- **`lift(h)`**: 姿勢を作ってから全関節を h だけ上げる。足が床に立っているという前提 (脚が届くか) の検査は外す。
- **`free`**: `SH2003` (速すぎる) と `SH2004` (両足が離れる) を出さない。`SH2002` (脚が届かない) は出す (骨は伸びない)。
- **相手の場所** (`b.hand` など): 相手の体幹 (骨盤・胸・頭・肩) は腕によらないので、そのまま読める。手だけは相手の腕の解に依存するので、
  **互いに相手の手へ伸ばしているときは、2 人の肩の中点から 0.25 m 下**を 2 人の目標にする (握手の高さで手が合う)。
  片方だけが伸ばすときは、相手の実際の手の位置。腕は届く長さまでしか伸びない (立ち位置は書き手が合わせる)。
- **`turn.b`**: 回り終わる時刻の相手の体重の位置を向く。相手がまだ解かれていなければ (宣言の順が後)、相手の立ち位置を向く。
- **`shift`**: 体重を両足の中点から足の側へ 85 % 寄せる。足は動かさない。

### 13.5 出力と CLI

- クリップが複数あるコマンドは、クリップごとにファイルを書く (`fighter.Idle.png`)。`--clip 名前` で 1 つ、`--score 名前` で `score` を選ぶ (出力は `入力-名前`)。
- **glTF は 1 ファイル**: 骨格は踊り手ごとに 1 つ、アニメーションはクリップごと (名前はクリップ名)。
  アニメーションの `extras` に `loop`、`velocity` (`inplace` のとき、踊り手ごとの [x, 0, z] m/s)、`marks` (`time` 秒、`name`、`figure`)。
- BVH と `.vrma` はクリップごと・踊り手ごとに別ファイルで、印などは横の `入力.events.json`。
- 踊り手の id (出力のファイル名やアニメーションの対象): `dancer` の名前。`figure` のないファイルで `dancer` も書かなければ `dancer`。
  `dancer` のない `figure` は `figure` の名前。

### 13.6 構文で決めたこと

- 1 行で書く項目 (`figure`、`dancer`、`music … score 名前`、ヘッダーの値) の後ろの部分は、**同じ行からしか取らない**。
  最上位の項目が後ろの行に依存しないことが、差分再パースの前提 (2 節の 5)。
- `a { steps {` は `figure` のブロック、`steps { left.fwd` は段、と先読みで分ける (`名前 { 名前 {` かどうか)。意味はバインダーが決める。
- 長さの単位 (`s` `f`) は数に空白なしで続く語だけを単位として読む。`fwd.-70` の `-70` は字句が負の数として読む。
- 長さ・`@`・`!` は語の後ろにどの順で書いても読む (サンプルに `@small:0.2s!stagger` と `:1@sharp!hit` の両方があった)。

## 15. 高さを足の置き場所から分ける (2026-11-14。実装済み、ユーザーの確認待ち)

14 節の「残っている不足」の 1 つ目への答え。`body { guard:8 }` と `steps { both.low@small both.low … }` を並べると、
「足は切れない」規則 (13.2) で構えの一歩が丸ごと落ちていた。

**決めたこと: `steps` の行は 2 つの部位を書く。足の置き場所 (`support`) と、その上に立つ高さ (`height`)。**

- `both.low` は高さだけを書く。足も体重も動かさない。
- 一歩と `together` は両方を書く (足の置き場所と、着いたときの高さ。書かなければ普通の高さ)。
  `turn` `jump` `shift` `lift` `land` は足だけ (跳躍は踏み切った高さに降りる、は今までどおり)。
- 重なりは部位ごとに解く。`support` は今までどおり切れない。`height` は身振りと同じで、狭い段が勝ち、
  負けた区間のあとは残りの時間で元の到着時刻に着く。

これで書けるようになったもの (どれも語を足していない):

```
section Idle loop           { body { guard:8 }  steps { repeat 4 { both.low@small both.low } } }   // 構えたまま弾む
section Sneak loop inplace  { body { walk:4 }   steps { both.low:4 } }                             // 同じ歩きを、腰を落として
```

「`both` は一歩を落とさない」という例外を足す案 (14 節) より、「高さは腕や頭と同じ 1 つの部位」とするほうが、
「狭い段が勝つ」という 1 つの規則のままで済む。

実装と、それに伴って変わったこと:

- `Channels.Height` を足した。`MotionIr` では一歩の `Seg` は `Level` を持たず、高さは `height` の列の `level` セグメントになる。
  段の狭さは `部位の数 (8) − 受け持つ部位の数` (`body` 0、`arms` と `steps` 6、1 部位 7)。
- 求解器は高さを、身振りと同じ `Chain` で読む (キーを通る曲線ではなくなった)。ループは身振りと同じく 3 周並べるだけでつながる。
  - **高さは 1 語ごとに止まる。** `both.high:2 both.mid:2 both.low:2` は mid でいったん止まる (以前は通り過ぎた)。
    サンプル 13 本の先頭クリップで動きが変わったのは `taiso` だけ (最大 5 cm)。
  - 高さにも `@sharp` `@linear` が効く。`both.low@sharp!x` の印は半分の時刻 (身振りと同じ)。

## 16. 小節線の規則と、繰り返しの書き方 (2026-11-14。16.1 と 16.2 は 16.5 で置き換えた)

### 16.1 小節線は「ここで小節が終わる」と言うだけ (取り下げ。16.5 の厳しい規則とタイになった)

以前の規則は「小節線が閉じる小節は、ちょうど 1 小節ぶんの拍を持つ」。だからイベントは小節線をまたげず、
3 拍の `move` を 3 拍目から置いた行や、`hold:8` のある行には小節線を 1 本も書けなかった (被験者 A は拍子を 2/4 に変えて逃げた)。

**決めたこと: 小節線は「前の小節線から、小節の整数倍の拍が過ぎた」ことを確かめる。** LilyPond の小節チェックと同じ考え方。

```
body { guard:0 | jab:2 kick:3 hold:3 | hold:8 | }     // 4/4。kick は 1 小節目の 3 拍目から 2 小節目へまたぐ
```

- またぐイベントの中には線を書かず、次に小節が終わるところに書く。
- 数え間違いの検査は残る (5 拍のところに書けばエラー)。エラーの後は、そこから数え直す (以前と同じ。1 つの間違いで後ろの線が全部エラーになることはない)。
- 小節線のある行は、行の終わりも小節の終わりでなければ警告 (以前と同じ)。
- 特別扱いが 2 つ消えた: `guard:0 | …` と `repeat 4 { … | }` の後の「何も入っていない小節線」は、0 拍 = 0 小節として規則どおり通る。
- `{ … } & { … }` の中の小節線も検査するようにした (以前は見ていなかった)。列は段の小節を共有する。`move` の定義の中の小節線は今も見ない (どこに置かれるか決まらない)。

退けた案: またぐことを示す記号 (タイのようなもの) を足す。書く量が増え、規則も増える。

ユーザーの問い (2026-11-14): またいで書けると一貫しない動作にならないか。Lily# ならタイでつなぐところ。検討の結果 (未決定):

- **動きは変わらない。** 小節線は検査だけで、動きを決めるのは長さ。線を書いても消しても同じ動きになる。
- **弱くなるのは検査。** 書いた線はどれも正しい小節の位置にあると確かめられるが、線の書き忘れは黙って通る
  (以前は次の線でエラー)。読み手は、線がないのが「またぐ意図」か「書き忘れ」かを区別できない。
- **曲を参照したときの拍子の変化。** セクションの途中で拍子が変わる曲では、変わり目をまたぐイベントの「拍」の長さが決まらない。
  `music` を実装するとき、拍子の変わり目をまたぐイベントはエラーにする。
- **タイを採らない理由。** 音は伸びている間どこも同じなので、小節線で切って 2 つに書いても意味が変わらない。
  動きは時間の中で一様ではなく、`kick:1~ | kick:2` の「1 拍と 2 拍」は蹴りの中の何にも対応しない。
  また `up:2 | up:2` (着いて、そのまま) と `up:2~ | up:2` (4 拍かけて着く) が記号 1 つで別の動きになる。
  止まっているだけの `hold` と `skip` は今も `hold:4 | hold:4` と切って書け、意味は変わらない。

### 16.2 繰り返しの一部だけ変える: 語は足さない (取り下げ。16.5 の `q` と `%` になった。狭い段で上書きする書き方は残る)

被験者 B は「2 回繰り返し、2 回目の手拍子だけ跳躍に」を、`section` を写して 8 行足して書いた。
だが今の文法で、繰り返しはそのままに、変えるところだけを狭い段に書ける:

```
steps { skip:16 | skip:3 jump.together:1 | }      // 2 回目の 4 拍目だけ跳ぶ

```

**決めたこと (提案): 構文は足さず、この書き方を文法書の `repeat` の項に載せる。** 12.3 の「繰り返しに別の終わりを付ける構文は足さない」のまま。
「狭く、後ろに書いたものが勝つ」という 1 つの規則が、変奏の書き方も兼ねる。16.1 で `skip:16 |` と書けるようになったので、数えるのも小節単位で済む。
文法書の以前の例 (`move pass` に包み直す) は、包み直しが要るように読めたので差し替えた。

退けた案 (ユーザーが採るなら実装する):

### 16.3 上書きされたイベントの印は出さない (不具合の修正)

### 16.5 繰り返しと小節線を Lily# に揃える (ユーザーが決定、2026-11-14。実装済み)

| 範囲 | 書き方 | 状態 |
|---|---|---|
| 小節より短い単位 | `{ … } q q` | ユーザーの案。下の規則は提案 |
| 小節 | `%` (直前の 1 小節)、`%N` (直前の N 小節) | ユーザーの案 |

`repeat` の今の使われ方 (サンプルと執筆試験の 9 か所): 小節ちょうどの単位が 6 (`%` で書ける。`trials/2/A/idle.shosa` は「3 回繰り返して 4 回目だけ違う」で `%` がそのまま当てはまる)、

`q` の規則 (提案): 「`{ }` は名前のない `move`、`q` はそれをもう一度」。

- 指すのは、同じ行でそれより前のいちばん近い `{ … }`。間のふつうのイベントは飛ばす (Lily# の `q` が和音だけを指すのと同じ)。`{ }` がなければエラー。
- 長さを書かなければ中身の長さ、書けば伸び縮み (`q:2`)。`@mirror` `@free` と印を付けられる。どちらも `move` と同じ。
- 届くのはその行の中だけ。`{ … } & { … }` の後の `q` は重ねた全体を繰り返す。
- Lily# と同じ意味の `q` (直前のイベント 1 つ) は採らない。「着く」イベントをもう一度書いても何も起きず、短い繰り返しの単位は 2 つのイベントの往復になるため。

`%` の規則 (提案): 小節線の間に単独で書く。繰り返す小節の端をまたぐイベントがあればエラー。`skip:16` は `skip:4 | % | % | % |` と書ける。

小節線 (ユーザー: 厳しいほうがよいように思えるが確信はない。今の書き方はタイの糖衣にも見える):

- 勧めは、**線はちょうど 1 小節を閉じる規則に戻し、またぐ動きはタイで書く**: `kick:1~ | :2` (`~` の後は長さだけ。Lily# の `c4~ 4` と同じ形)。
  1 つのイベントで、長さは合計。`@` と印は最初のほうに書く。
- 理由: (1) 16.1 の書き方は、小節線が伝えるはずの「どこで小節が変わるか」をちょうどまたぐところで隠す。(2) 並んだ段の小節が縦にそろう。
  (3) 書き忘れを拾える。(4) 曲の拍子が途中で変わっても、切れた各部分は 1 つの小節の中にあるので長さが決まる。(5) `%` が小節を単位にする。
- 16.1 で挙げたタイへの反対のうち、「切った長さが動きの何にも対応しない」は残るが害はない。「`up:2~ | up:2` と `up:2 | up:2` が別の動き」は、
  語を繰り返さない `:2` の形にすれば起きない。


### 16.6 16.5 の実装で決めたこと (2026-11-14)

ユーザーが 16.5 の表のとおりで良いと決め、実装した。**12 節から 15 節に出てくる `repeat N { }` と `form { B*2 }` は古い書き方**で、今はない。全体は GRAMMAR_FOR_LLM.md の "Doing it again"。

- **構文**: `{ … }` 1 つだけの重ね書きがまとまり (構文木では `Overlay`)。`q` は語 (`Vocabulary.Again`、定義の名前には使えない)。
  `%` `%N` は `BarRepeat`、タイはイベントの末尾の `~` と、目標のないイベント (`:2`)。`form` は `FormSign` (`|:` `:|` `:|*N` `:|:`) と `FormEnding` (`[1. B]` `[1-2. B C]`)。
  `]` は `:|` の直前でだけ省ける (Lily# と同じ)。`-]` (括弧の右端の形) は楽譜の話なので読まない。
- **`q` が指すまとまりは、書かれた位置で決まる** (同じ段の中で、`q` より前に閉じた `{ }` のうち最後のもの)。入れ子は外側が勝つ。
  実行の状態ではなく位置で決めるので、`%` や別の `q` がたどり直しても同じものを指す。
- **`%` は、その行がそこまでに行ったことの記録から、直前の小節ぶんをもう一度行う。** 印も繰り返す。`:0` は繰り返さない。
  `%` の中の `q` や定義した語もそのまま働く。`%N` の後の小節線は 1 小節を閉じる (`a | b | %2 | %2 |`)。
- **`q` と `%` で行われたイベントのソース位置は、`q` や `%` の位置** (プレビューで光るのも、`SH2xxx` が指すのも、書いた場所。`move` と同じ考え方)。
- **タイ**: 1 つのイベントで長さは合計。間の小節線は、その位置で検査する。`@` と印は最初の部分に書く。定義した語にも `q` にも付けられる。
- **小節線**: 元の規則 (ちょうど 1 小節) に戻した。何も入っていない線は今までどおり区切りとして通る (行の先頭、`guard:0 |`)。
  Lily# の「空の小節は 1 小節ぶんの休み」は採っていない。**→ 後で採った (29 節)。行の先頭の線も `guard:0 |` の線も、いまは空の小節。**`{ … } & { … }` の中の線は今も検査し、いちばん長い列の小節の位置が外へ続く。
- **`form`**: 反復の入れ子は不可。終わりのある反復では、1 から最大の番号までのどの回にも、ちょうど 1 つの終わりが要る (Lily# と同じ)。`B*2` はエラーにして書き方を示す。
- **古い書き方への案内**: `repeat N {` は構文エラー `SH0012` で、代わりの 3 つの書き方を示す (波括弧の中は 1 回だけ行う)。
- **足した診断**: `SH0012` (`repeat`)、`SH1025` (`form` の反復)、`SH1026` (`q` の前にまとまりがない)、`SH1027` (`%` が単独でない、前に小節がない、タイがかかっている)、`SH1028` (タイの相手がない)。
- VS Code の色づけ: `q`、`%` `%N`、`~`、`|:` `:|` `:|:`、`[1.` `]` (2026-11-14。`npm run build` と `npm run check` は通る。VS Code で見てはいない)。補完は `q` を出す。
  `trials/2/` の被験者のファイルのうち `repeat` を使う 5 本 (`idle` `taunt` `sneak` `linedance` `linedance-edit`) は、当時の記録なので直していない (今はエラーになる)。
  新しい文法書での執筆試験は 17 節。

### 16.7 長さを音価で書くか (ユーザーが決定、2026-11-14: 拍のまま。音価は、必要になったら単位として足す)

ユーザー: ここまで Lily# に寄せるなら、長さは拍数より音価で書くほうが良くないか。12.10 の 2 で「一旦、拍」と決めた点の見直し。

- **事情が変わった点**: 当時の反対の 1 つ目は「長い動きにタイが要る」だった。厳しい小節線とタイを入れたので、小節線のある行ではどのみち
  1 小節より長いイベントは書けず、この反対はほぼ消えた。
- **音価の良い点**: `.lys` と数の意味が同じになる。6/8 などで「1 拍」を決めなくて済む。
- **残る反対**: (1) 相手はプログラマーと AI で、音楽を参照しないクリップも対等に扱う (ROADMAP 1 節)。`hold:3` は誰でも読めるが `hold:2.` は楽譜の知識が要る。

  小節線のない行 (ゲームのクリップ) の 5 拍や 7 拍は、綴りのためだけにタイが要る。(3) 秒とフレーム (`:0.3s` `:12f`) は「時間の量」で、拍数とは並ぶが音価とは向きが逆。

ユーザーの問い (同日): 拍数と音価の両方をサポートすれば解決するか。検討 (未決定):

確かめたかったこと (16.5) への答え:

- **タイは煩わしくないか。** A は「自然」と書いた (`back.high:2@bent~ | :1 fwd:1@sharp!hit guard:2~ | :1 skip:3 |`。小節の検査が溜め 3 拍・戻り 3 拍の置き場所を保証した)。
  B は、どの動きも 6 拍の太極拳では「書けるが読み返しにくい」と書いた (`both.low:4~ | :2 left.side.low:2~ | :4 |`。切る場所がイベントごとに違い、後半の `:4` からは何の動きか読めない)。
  ふつうの頻度なら問題なく、またぐのが常態の振付では重い。
- **`q` `%` `form` の反復記号**は 2 体とも初回で正しく書け、「自然」に挙げた。`%` の 1 小節を書き出す修正 (文法書の案内どおり) で A の修正は 1 行で済んだ。

直したもの:

| 見つかったこと | 対処 |
|---|---|
| `SH1002` の案内が決まり文句 `kick:1~ \| :2` で、`kick` のないファイルにも出て、数も合わない | またいでいるイベントから求める: `'kick' runs across the bar line: tie it over, kick:1~ \| :3`。見つからなければ「as in」と断る |
| `sheet --view top` (ない値) が黙って正面の絵になる | エラーにする |
| 印が連続写真に出ない (14 節の残り) | その瞬間か直後のコマに緑で `!HIT` と書く。コマがちょうどでなければ拍も (`!HIT 5.5`)。3×5 の字形に英字を足した (すべて大文字で描く) |
| 文法書の不足 | 拍は 0 から数えること (`check` も)、「3 拍目に手拍子」は 2 で終わるイベントであること、定義した語のタイは書いた長さの合計であること (`kick:1~ \| :3`)、`%N` の中どうしのタイはよいこと・`%` は前の `section` に届かないこと・`:0` は繰り返さないこと、`shift` は高さを変えないこと、`--score` で 1 人だけ大きく見られること |

残っている不足 (設計が要る。決めるのはユーザー):

- **`skip` の埋め草。** 2 体とも、いちばん煩わしいものに挙げた。何かが起きる小節まで `skip:4 | skip:4 | skip:4 |` と書き、
  小節線のある行は最後の小節も埋める (`taunt` は 3 行の文字の半分、`greeting` は 14 小節ぶん)。`%` は手拍子の小節の後では手拍子を繰り返すので使えない。
  16.6 で採らなかった「何も入っていない小節は 1 小節ぶんの休み」(Lily#) か、複数小節の休み (`skip` を小節で数える書き方) が候補。
  前者は行の先頭の線と `guard:0 |` の線 (今は区切り) と衝突するので、その 2 つをどう扱うかを含めて決める。
- **定義した長さのまま小節をまたぐ。** `kick~ | :3` は 4 + 3 拍になる (規則どおりだが、被験者は「定義の長さから引き算する」ことになった。定義を変えると黙って伸び縮みする)。
  案: 長さのない語にタイが付いたら「定義した長さを、ここで切る」と読み、後ろの長さが残りと合わなければエラー。ふつうの目標 (`up~ | :1`) の読み方と割れるのが難点。
- **`%4` の最後の 1 小節だけ変える。** `%N` は「直前の N 小節」しか指せないので、4 小節を書き出すことになった (B の修正)。`steps` はいちばん狭い段なので、上書きもできない。
  `section` に分けて `form` の `[1. …] [2. …]` を使えば書けるが、書き直しが大きい。
- **着いた瞬間が拍の頭になるようにずらす手間。** 「イベントは終わりで着く」ので、拍の頭の手拍子は前の準備と合わせて数える。`@sharp` は半分の時刻に着くので、拍ちょうどに当てるには半分前から始める。
  2 体とも正しく書けたが、「毎回考えた」と書いた。
- **経由点のある 1 つの動き。** 正反対への腕 (`side` → `across`) は `fwd:3 across:3` と割るので、6 拍の 1 つの動きが 3 + 3 になり、まん中で緩む。
- ~~**届かない接触への診断がない。**~~ 足した (`SH2006` `SH2007`。18 節)。 `b.shoulder` に手が届かなくても「no problems」。足りない距離を警告に出せる。踊り手どうしの重なり (1 m で向き合って 30 度の礼をすると頭が当たる) も同じ (14 節)。
- **語の不足**: 体重を乗せない足の一歩 (ステップタッチの「タッチ」)、少しだけ膝を曲げて着く一歩 (一歩の `@small` は歩幅)、`.high` より上の手の高さ。
  `low` の構えは被験者の想像より深い (太ももが水平に近い)。
- **絵の読みにくさ**: 頭の向きは鼻の線が短くて確かめにくい。3 人だと 1 人が小さい (`score solo { dancer bea }` と `--score` で回避した)。
  `b.shoulder` が相手のどちらの肩か、絵からは決められなかった。

第 2 段階の判断の材料として: 3 回の試験で 32 ファイルすべてが診断なしになり、今回は 12 本のうち 10 本が 1 回目の `check` で通った。
頼まれた動きに届かなかった点は、上の語の不足と、文法の外 (肩、手のひら) にある。


## 18. 接触と重なりの診断、歩く足の返し (2026-11-14。実装済み)

17 節の「設計なしで進められるもの」と、ROADMAP の求解器の手直しの 1 つ。どれも文法は変えていない。

| 番号 | 内容 | 決め方 |
|---|---|---|
| `SH2006` (警告) | 相手の場所へ伸ばした手が届かない。足りない距離を言う (`ben's shoulder is about 0.28 m farther than the arm reaches`) | 腕の `reach` が着く時刻 (`T1`) に、肩から目標までの距離が腕の長さ (0.60 m) を 3 cm より超えていれば出す。着く前に狭い段に取られた `reach` は見ない。`free` でも出す (腕の長さは物理ではなく体) |
| `SH2007` (警告) | 踊り手どうしが同じ場所にいる。組ごとに 1 回、最初の拍を言う | 頭 (半径 0.10 m の球) と胴 (骨盤から胸までの線分、半径 0.11 m) だけを比べる。腕と脚は見ない (手は合わせるもの、当たる蹴りは意図)。指す場所は、その時刻に動いている `torso` `steps` の語、なければ `section` |

- `inplace` のクリップでも、重なりは移動を抜く前の位置で比べる (エンジンの中での位置)。
- 3 回目の試験のファイルで確かめた: `trials/3/B/greeting.shosa` は肩に 0.28 m、頭上のハイタッチに 0.11 m ずつ届いていなかった (被験者の報告どおり)。
  `trials/3/B/linedance.shosa` は 26.87 拍で ann と bea の胴が重なる (`mirror` の踊り手が回転の後に逆へ進むため。14 節の「`mirror` と回転」が原因で、連続写真でも重なって見える)。
  `samples/` の 13 本には出ない。

  「近いほうの肩」にする案がある (向き合っても、後ろに並んでも自然)。横に並んで肩を組むときだけ遠いほうが欲しくなる。

**歩く足の返し。** 遊脚の足が床と平行のまま浮いていた。前へ出る一歩は、前半でつま先を残してかかとから離れ (足首まわりに最大 0.6 rad)、
後半でつま先を上げてかかとから着く (最大 0.5 rad)。後ろへの一歩は逆。大きさは、一歩が足の向きへ進む距離 (歩幅 0.5 m で 1) に比例し、真横の一歩では 0。
回転 (`turn`)、跳躍、脚のしぐさには付けない。書き出す骨の回転は足首からつま先への向きから求めるので (9 節)、BVH・glTF・`.vrma` にもそのまま出る。
連続写真 (`walk --view side --step 0.0625`) で見た。VRM モデルではまだ見ていない。


## 19. 曲の参照の実装 (第 2 段階の 3 の 6、2026-11-14。実装済み。プレビューの音は 19.6。ユーザーが VS Code で聞いた。音源は 23 節でサウンドフォントに)

12.8 の設計を実装した。`music "song.lys"` と書くと、テンポ・拍子・セクションの順が曲から来て、曲の全体が 1 本のクリップになる。
`samples/dance.shosa` が `samples/song.lys` (108、4/4、Verse と Chorus が 4 小節ずつ) に合わせて 32 拍で通る。

### 19.1 Lily# は別の実行ファイルから読む

| 部品 | 役割 |
|---|---|
| `Shosa.Music` (`shosa-music.exe`) | **Lily# に触れる唯一の場所。** `LilySharp.Core` をプロジェクト参照し (`..\..\LilySharp`。nuget.org にはなかった)、`timeline` (JSON)、`midi`、`wav` を出す |
| `Shosa.Core/Music/SongReader.cs` | `shosa-music` を起動して JSON を受ける。Lily# は何もリンクしない。答えは (曲のファイルの更新時刻、score、順) ごとに覚える |
| `Shosa.Core/Semantics/Song.cs` | `SongInfo` (テンポ、拍子、セクションの名前、演奏順と各回の長さ・弱起、注意)、`SongSource` (読む口)、`MusicIr` (クリップが持つ「どの曲を、どの順・テンポで鳴らすか」) |

- **分けた理由は 2 つ。** Lily# は GPLv3 以降で、しかも LilyPond 由来のコードを含むので、作者でもライセンスを替えられない。リンクするとその実行ファイルは GPL になる。
  もう 1 つは重さで、`LilySharp.Core` は楽譜を彫る部品 (SkiaSharp、HarfBuzz、PdfSharpCore、フォント) を連れてくる。
  分けたので、GPL になるのは `shosa-music` だけで、`Shosa.Core` `shosa` `shosa-lsp` のライセンスは第 4 段階で自由に決められる。
  `shosa-music` のソースには GPL の断り書きを入れた。
- バインダーは曲がどこから来るかを知らない (`Binder.Bind(tree, score, songs)` の `SongSource`)。試験は手書きの `SongInfo` を渡す。
  口がなければ (テキストだけをコンパイルした) `SH1900` (情報) を出し、ファイルに書いてあるものだけで解く。
- `shosa-music` の探し方: 環境変数 `SHOSA_MUSIC`、実行ファイルの隣か `music\`、開発中は `Shosa.Music\bin\<構成>\net10.0`。配布のときの置き場所は第 4 段階で決める。
- 起動は曲ごと・順ごとに 1 回 (0.3 秒ほど)。言語サーバーは打鍵のたびにコンパイルするが、曲のファイルが変わらなければ起動しない。
- **`.lys` を保存すると、開いている踊りの診断とプレビューが新しくなる** (2026-11-14)。拡張が `**/*.lys` を見張り、
  言語サーバーは `workspace/didChangeWatchedFiles` を受けて、`music` と書いてある開いた文書をコンパイルし直す。
  どの曲が変わったかは見ない: 読み直すかどうかは `SongReader` がファイルの更新時刻で決めるので、変わっていない曲には何も起動しない。
  見張るのはワークスペースの中だけ。`using` で読まれる先の変更は見ない (覚えている答えの鍵が曲のファイルの時刻だけなので)。

### 19.2 曲から受け取るもの

`shosa-music timeline SONG.lys [--score 名前] [--order "A B A"]` が出す JSON が `SongInfo` になる。中身は `MidiExporter` が出す `MidiFile` から求める (12.8 の「Lily# の口」)。

- **拍**は拍子の下の数の音符。6/8 の曲は 1 小節 6 拍で、テンポは 8 分音符の数 (`greensleeves.lys` の `tempo 60` は 120 になる)。
- **演奏順と長さ**は `SectionStarts` の差。最後のセクションは最後の小節線まで (`EndTick` だとフェルマータの分だけ長くなった: `harbour-lights.lys` が 36 拍でなく 38 拍)。
- **弱起**はセクションごとに持つ (`SongPlay.Pickup`)。セクションの最初の小節線が 1 小節ぶんより手前にあれば、そこまでが弱起。
  踊りはその小節線から始まり、セクションに入る長さは弱起を引いた残り (`greensleeves.lys` の Verse は 49 拍で、弱起 1 + 8 小節)。
- **`.shosa` の `form` で順を変える**ときは、曲のテキストの末尾に `form ShosaOrder__ { … }` を足してから Lily# に解かせる (12.8 の案のとおり)。
  セクションのつながり方 (弱起の扱いなど) は Lily# の規則のままになる。曲にない名前は `shosa-music` が落とし、バインダーが `SH1005` を出す。
- **テンポを変える** (`tempo N`) ときは、`MidiFile` の全トラックのテンポ変化に同じ比を掛ける。ティックは動かないので拍の位置は同じ。
- 途中でテンポや拍子が変わる曲は、変化の一覧 (`SongInfo.Tempos` `SongInfo.Meters`) を返し、踊りがそれに付いていく (21 節)。
  はじめは `SongInfo.Notes` と警告 `SH1904` で「最初のテンポと拍子で数え続ける」と言うだけだった。どちらもなくした。

### 19.3 バインダーの規則

| 番号 | 内容 |
|---|---|
| `SH1900` (情報) | 曲を読む口がない。ファイルに書いたテンポ・拍子・構成で解く |
| `SH1901` | 曲を読めない (ファイルがない、`.lys` にエラー、`score` がない、`shosa-music` がない)。理由は曲の側の言葉で言う |
| `SH1902` | 曲があるのに `time` を書いた (12.8: 上書きできない) |
| `SH1903` | `section` が曲の同じ名前のセクションより長い。曲の側の拍と小節の数を言う |
| ~~`SH1904`~~ | なくした (曲が途中でテンポか拍子を変える、という警告だった。21 節で付いていくようになった) |
| `SH1905` (警告) | 曲にない名前の `section`。踊られない |

- 曲を読めたら、クリップは曲の全体の 1 本 (名前は `form` のクリップと同じ決め方)。`section` は曲の同じ名前のセクションが鳴るたびに踊る。
  短ければ残りは止まり、`.shosa` にないセクションは立ったまま通る (`SectionIr` の出どころは `music` の行)。
- テンポは、書いてあれば上書き、なければ曲のもの。**拍・秒・フレームの換算はテンポに頼るので、曲はほかの何より先に読む。**
- `form` があれば、その順を曲に渡して長さを受け取る。`form` の名前は曲のセクションの名前で、`.shosa` に `section` がなくてもよい。
- **曲を読めなかったとき (`SH1900` `SH1901`) は小節線を検査しない。** 拍子は曲のものなので、分からない拍子で `SH1002` を並べない。
  この場合クリップは曲なしのときと同じ形 (`form` がなければ `section` ごと) で、`Music` は付かない。
- 決めていないこと: `delay` のある踊り手がいるとクリップが曲より長くなる (14 節の「`delay` と決まった長さ」と同じ問題)。
  `dancer … in` に曲だけにあるセクションの名前は書けない (`SH1005`)。

### 19.4 CLI

### 19.6 プレビューの音 (2026-11-14。実装済み。**耳での確認はユーザー待ち**)

19.5 の (a)。曲に合わせたクリップを VS Code のプレビューで再生すると、曲が鳴る。同梱するものはない。

| 部品 | 役割 |
|---|---|
| `shosa-music notes SONG.lys [--score] [--order]` | 音符の一覧を JSON で出す。1 音は `[始まる拍, 長さ (拍), 高さ (MIDI 番号。.5 は四分音), 強さ (1-127), 音色]`。音色は Lily# のプレビュー用の分類 (0 ピアノ … 8 声、9 はドラムで高さは GM のドラム番号) |
| `SongReader.Notes(MusicIr)` | `shosa-music` を起動して受ける。(曲、score、順) ごとに 1 つ覚え、曲のファイルの更新時刻が変われば読み直す |
| 言語サーバーの `shosa/song` (要求) | `{ uri, file, score, order }` → `{ error, notes }`。クリップの `music` をそのまま渡す |
| 拡張 (`extension.ts`) | プレビューの `song` メッセージをサーバーへ取り次ぐ |
| プレビュー (`main.js` の「Sound」) | WebAudio で鳴らす |

- **拍は踊りの拍で、時計は人形の時計 1 つだけ。** 音符は拍で届き、プレビューは毎フレーム「今の拍から 0.15 秒先までに始まる音」を WebAudio に渡す。
  時刻は人形のいる拍から計るので、速度 (0.25 倍など) を変えても、シークしても、ループしても、音は動きからずれない。
  音のファイルを流す方式 (b) だと、再生位置を 2 つの時計の間で合わせる仕事が要る。
- 止める・シークする・別のクリップへ移ると、鳴っている音は 1 回のフェードで止まる (再生 1 回ぶんの出口を 1 つの gain にまとめてある)。
  踊りを編集しても曲は同じなので、再生中の音は続く。ループの継ぎ目では、最後の音は鳴らしたまま頭に戻る。
- 音符は Play のたびに頼み直す。サーバーは `.lys` が保存されていなければ覚えている答えを返すので、`.lys` を直して保存すれば次の Play で新しい曲になる
  (診断のほうは `.lys` の保存で新しくなる。19.1)。
- 音色は発振器 (三角波、のこぎり波など) とノイズだけ。旋律と拍が聞き取れればよく、曲の仕上がりの音ではない。仕上がりは `shosa midi` / `shosa wav`。

### 21.1 決めたこと (ユーザーの確認待ち)

| 決めたこと | 理由 |
|---|---|
| **拍は、そのとき有効な拍子の下の数の音符。** 4/4 から 6/8 に変わると、そこから 1 拍は 8 分音符で、1 小節は 6 拍 | 19.2 の「拍は拍子の下の数」をそのまま伸ばした。`check` の「N to the bar」と小節線の数え方が、どの小節でも「書いてある拍子の上の数」で合う。退けた案: 最初の拍子の音符で数え続ける (6/8 の 1 小節が 3 拍になり、8 分で踊る動きが `:1/2` だらけになる) |
| **テンポは、その拍で数える。** 4 分 = 100 のまま 6/8 に入ると 200 と言う | 拍・秒の換算が「拍 × 60 / テンポ」1 つで済む。音楽の速さは変わらないのに数が変わるのは、拍の長さが変わったから |
| **テンポの変化は拍を動かさない。変わるのは、その後の拍の秒だけ** | 振付は拍で書いてあり、書き直すものがない。フレームは秒で等間隔なので、1 フレームに入る拍の数が変わる |
| **`.shosa` の `tempo N` は「曲が始まるテンポ」。** 後のテンポは同じ比で変わる | 12.8 と `shosa midi` (全部のテンポ変化に同じ比を掛ける) がすでにこの形。踊りと書き出した曲が同じ速さになる |
| **`:0.3s` と `:12f` は、そのセクションが始まるテンポで拍に直す。** セクションの途中でテンポが変わっても数え直さない | セクションの長さ (`SectionLength`) と `move` の長さ (`Natural`) は場所に依らず 1 回だけ求めている。途中の変化まで追うと、同じ `move` の長さが使う場所ごとに変わる。**不正確になるのは「テンポが変わるセクションの、変わった後に書いた秒・フレーム」だけ** |
| 定義 (`move`) の中の `%` は最初の拍子の小節 | 定義は場所を持たない |
| 警告 `SH1904` と `SongInfo.Notes` はなくした | 言うことがなくなった |

Lily# の側の規則で、知っておくこと: **セクションが変わるとテンポと拍子はファイルの頭のものに戻る** (`turning.lys` の Waltz は 120 に戻り、`time 3/4` はセクションの中に書く)。
Shosa は MIDI に出たとおりに受け取るだけ。リタルダンドのような連続した変化は、Lily# が段にして出したぶんだけ段になる (試していない)。

### 21.2 受け渡し

- `shosa-music timeline` の JSON に `tempos` (`[{beat, bpm}]`) と `meters` (`[{beat, beatsPerBar, beatUnit}]`) が加わった。どちらも最初の項は 0 拍。
  ティックから拍へは拍子の区間ごとに直す (`SongFile.Beat`)。`plays` の長さ・弱起、`notes` の拍も同じ関数を通る。
  拍の単位が変わるところでは、音楽のテンポが同じでも `tempos` に 1 項入る。
- `SongInfo.Tempos` `Meters` → `MotionIr.Tempos` `Meters` → `MotionClip.Tempos` `Meters`。`Tempo` `BeatsPerBar` は「最初の値」として残した。
  手書きの IR で一覧が空なら、その 1 つの値だけの地図になる (`TempoMap.Of` `Bars.Of`)。
- 換算は `TempoMap` (拍 ↔ 秒) と `Bars` (小節。`At` `Count` `MeterAt`) の 2 か所。`MotionClip.SecondsAt` `FrameAt` `BeatOfFrame` はこれを通る。
  プレビューの JS は同じ式を `editors/vscode/src/preview/time.js` に持つ (`sound.js` と同じく 2 つのプレビューが共有し、`Shosa.Core` が埋め込む)。

### 21.3 各部

- **バインダー**: 段を歩く前に「いま曲のどこか」を置く (`Place`)。小節線の検査、`%` の長さ、段の最後の小節の検査は、その場所の拍子で数える。
  `SH1002` は拍子が最初と違うとき「曲が途中で拍子を変える。`shosa check` が場所を言う」と添える。`SH1903` は拍子が変わるセクションでは小節の数だけ言う。
  **曲を読めなかったとき** (`SH1900` `SH1901`) は拍子が分からないので、`%` は「同じ段で直前に小節線が閉じた小節の長さ」をもう一度やる
  (それまでは 4/4 と仮定していて、3/4 の見本を曲なしでコンパイルすると `SH1027` になった)。
- **求解器**: フレームごとの拍を地図から求める。跳躍の滞空時間は地図の秒。印の秒、`inplace` の速度も同じ。
- **`check`**: `at 120 beats a minute (90 from beat 12, 120 from beat 16), 4 to the bar (3 from beat 16): March 0-16 (4 bars), Waltz 16-28 (4 bars)`。
- **連続写真**: 太字 (小節の頭) は拍子の変化に付いていく (`turning` の Waltz は 16, 19, 22, 25)。
- **プレビュー (2 つとも)**: 時計は秒で進み、拍は地図から求める。音は拍に付いたままなので、テンポが変わるところでも動きからずれない (先読み 0.15 秒ぶんだけ、変わり目で前のテンポの長さになる)。
- BVH・glTF・`.vrma` はフレームが秒で等間隔なので、何も変えていない (印の秒は地図を通る)。

## 22. 設計なしで進めた仕事 (2026-11-14。実装済み)

### 22.1 `music` の行の補完 (19.5 の残り)

| カーソルの場所 | 出るもの |
|---|---|
| `music "` の引用符の中 | `.shosa` の隣と 1 つ下のフォルダーの `.lys` (近いものが先。区切りは `/`) |
| `music "song.lys" ` の後 | `score` (`score { }` の中なら、続けて書ける `form` `tempo` … も) |
| `music "song.lys" score ` の後 | その曲の名前つきの `score` (`SongInfo.Scores`。名前のない既定のものは出さない) |

- 場所の判定は行の文面から (`Words.AtMusic`)。`score { tempo 60 music "x.lys" score k }` のように 1 行に続けて書いても効く。
  ファイルと曲の中身は `Words.Songs` (ファイルの一覧を返す口と、曲の `score` を返す口) から来るので、`Words` はディスクを知らないまま。
- **ファイル名には `textEdit` を付ける** (引用符の後からカーソルまでを置き換える)。名前には `.` や `-` があり、エディターの「語」で置き換えると
  `my-so` の `so` だけが替わって `my-my-song.lys` になる。
- `"` を補完の引き金に足した。`title "` では何も出ない。
- `score` の一覧は曲を既定の `score` で読んだ答え (`SongReader` が覚えているもの) から取るので、打鍵ごとに `shosa-music` は起動しない。

### 22.2 ホバーに定義の長さ (13.9 の残り)

- `move` の名前のホバーが「長さを書かなければ N 拍。書けばその長さに伸び縮みする」と言う。`pose` は「1 拍で着く」。使った場所でも、定義した場所 (`move jab {` の `jab`) でも同じ文。
- 長さはバインダーの `Natural` (いちばん長い段)。`ScoreIr.MoveLengths` に載せて言語サーバーへ渡す (IR のクリップには入れない: 定義はクリップに属さない)。
  秒・フレームで書いた `move` は、曲が始まるテンポでの拍 (21.1 と同じ)。

### 22.3 プレビューに印を描く (13.10 の残り)

- 印 (`!hit`) の拍ごとに、シークバーの下に緑の目盛り。印が着いた瞬間から 0.6 秒のあいだ、舞台の左上に `!hit` と出る
  (踊り手が 2 人以上なら `!clap bob, carol` と誰のものかも。同じ名前は 1 回だけ書く)。
- **0.6 秒は拍ではなく時計**。テンポが遅くても速くても読める長さで、止めて印の拍に合わせれば出たままになる。速度 0.25 倍でも拍に付いている (人形の時計で計る)。
- 「どの印がいま出ているか」と文面は `time.js` の `marksAt` `markText` (2 つのプレビューが共有。`npm test` の `time.test.mjs` に試験)。目盛りと表示の DOM は 2 つのプレビューにそれぞれ書いた。
- 目盛りの位置は、スライダーのつまみの幅 (16 ピクセルと見なす) を引いた幅の上に置く。つまみの幅はブラウザーごとに違うので、数ピクセルずれることはある。
- **見たもの**: `shosa preview samples\fighter.shosa --clip Combo` のページを Chrome で開き、目盛り 6 本と、1 拍目に `!hit   !step` が出ること、コンソールにエラーがないこと。
  **VS Code のプレビュー (`main.js`) は、ビルドと型の検査だけで、動かして見てはいない。**

### 22.4 連続写真の字 (21.5 の残り)

- 3×5 の点の大文字だけの字をやめ、**5×7 の点の字 (ASCII の印字できる字すべて、大文字と小文字は別の形)** にした。`N` `H` `M` `W` は 3×5 では 1 点ずつしか違わず、直しようがなかった。
  名前は書いたとおりに出る (`alice`、`Verse`、`!clap`)。字形は昔からある 5×7 のドットマトリクスのもの。`g j p q y` の尾のために 1 行ぶん下を使う (1 字は 6×8 の枠)。

  コマの高さを 250 → 264、床の線の下を 26 → 40 (名前 2 段ぶん) に広げ、印の行の間隔を 18 にした。数は `ContactSheet` の定数 (`TextScale` `Advance` `LineHeight` `UnderFloor`) から出る。

### 22.6 VS Code で曲が見つからなかった (不具合の修正)

- ユーザーが開発ホストで `samples\dance.shosa` を開くと、`music "song.lys"` に `SH1901` (隣に `song.lys` がない) が出た。曲に合わせる踊りを VS Code で開いたのはこれが初めて。
- 原因: VS Code は Windows のドライブのコロンを `%3A` と書く (`file:///c%3A/MyProj/…`)。.NET の `Uri.LocalPath` はそれを `/c:/MyProj/…` と返し、
  `Path.GetFullPath` が `C:\c:\MyProj\…` にしていた。試験は `new Uri(path).AbsoluteUri` (`file:///C:/…`) を使っていたので通っていた。
- 直し: 言語サーバーの `PathOf` 1 か所で URI をパスにする (頭の `/c:` の `/` を落とす)。曲の読み込み、`shosa/song`、補完が同じ道を通る。試験は `%3A` の URI でも曲が読めることを見る。


## 23. プレビューの音をサウンドフォントで鳴らす (2026-11-14。実装済み、VS Code での耳の確認はユーザー待ち)

### 23.1 決めたこと

| 決めたこと | 理由 |
|---|---|
| **シンセは Lily# の拡張と同じ `spessasynth_lib`** (Apache-2.0。`spessasynth_core` 4.3.22 と `spessasynth_lib` 4.3.14 に固定) を、プレビューの webview の中で動かす | 時計が 1 つのまま (19.6)。音符を 1 つずつ、人形のいる拍から計って渡すので、速度・シーク・ループ・テンポの変化で動きからずれない。WAV を流す (b) だと時計が 2 つになる |
| Lily# の拡張のコード (`previewSynth.ts` `playbackCore.ts`、GPL) は写さず、`spessasynth_lib` の上に自分で書いた | 拡張のライセンスを GPL に縛らない (19.1 と同じ考え)。GPL なのは `shosa-music` だけのまま |
| **サウンドフォントは同梱しない。Lily# が鳴らすものを探して使う** | 曲が、自分のプレビューと踊りのプレビューで同じ音になる。40 MB を Shosa の拡張に入れずに済む |
| 探す順: `shosa.playback.soundFont` (新しい設定) → `lilysharp.playback.soundFont` → 拡張 `yotsuda.lilysharp-soundfont` の `soundfont\` の最初の `.sf2/.sf3/.dls` → OS の GM バンク (Windows の `gm.dls`、macOS の `gs_instruments.dls`) → なし | 後ろ 3 つは Lily# の拡張と同じ順。なければ今までの発振器の音 (`sound.js`) で鳴る |
| **フォントを読み終えるまでは発振器で鳴らし、読めた拍から切り替える** | 最初の Play を待たせない。ブラウザーは音のスレッドをクリックの後にしか動かさず、シンセの組み立てとフォントの解析はそのスレッドで進むので、最初の Play の前には終えられない (フォントのファイルを取ってくるところまでは先に済ませる) |
| `shosa preview` の HTML は発振器のまま | ディスクの 1 枚のページは、この機械の 40 MB のファイルを読めない |

### 23.2 各部

| 部品 | 役割 |
|---|---|
| `shosa-music notes` | 1 音に 2 つ足した: `[拍, 長さ, 高さ, 強さ, 音色, プログラム (GM 0-127。パートが言わなければ -1), チャンネル (0-15。9 はドラム)]`。プログラムは書き出す MIDI と同じ (`MidiTrack.Program`) |
| `preview/fontsound.js` | タイミングだけ。`sound.js` のプレーヤーと同じ形 (`start` `setSong` `cue` `play` `rewind`) で、それを中に抱える。シンセには「口」(`ready` `now` `program` `noteOn` `noteOff` `bend` `quiet`) を通して話すので、偽の口で試験できる |
| `preview/synth.js` | 口の実体。`WorkletSynthesizer` を作り、フォントを読み、状態 (`none` `loading` `ready` `failed`) を知らせる |
| `extension.ts` | フォントを探す (`soundFontFile`)。webview にそのフォルダーを読ませ (`localResourceRoots`)、`synth` メッセージでワークレットとフォントの URL を渡す。設定が変われば渡し直す。CSP に `connect-src`、`'wasm-unsafe-eval'`、`blob:` を足した |
| `build.mjs` | `spessasynth_processor.min.js` を `dist\` に写す (ワークレットは別のファイルで読ませる) |

- 楽器はチャンネルごとに 1 回言う (止めた後はもう一度)。プログラムのないパートは音色の分類から GM の楽器を当てる (ピアノ 0、フルート 73、クラリネット 71、弦 48、ギター 24、ベース 33、金管 61、オルガン 19、声 52)。
- 音の終わりは、その音を渡したときのテンポで決める (鳴っている途中で速度を変えても、その音の長さは変わらない)。同じ鍵をすぐ打ち直せるよう、終わりを 0.01 秒早める。
- 止めるとき: シンセは渡された出来事を時刻順に持っているので、最後に渡した音の後ろに All Sound Off を入れ、次の音はその後から始める。
- 四分音は下の鍵とピッチホイール (1 チャンネルに 1 つなので、同じチャンネルで同時に鳴る音も曲がる。書き出す MIDI と同じ制限)。**ペダルは渡していない** (音符の長さは書いたまま)。
- 「Sound」のチェックにカーソルを置くと、何で鳴っているか (フォントの名前、読み込み中、なぜ発振器か) が出る。

## 24. VS Code 拡張のパッケージとアイコン (2026-11-14。第 4 段階の先取り。公開はまだ)

ユーザーの依頼で、インストールできる `.vsix` を作れるようにした。**Marketplace には出していない。**

- **作り方**: `tools\pack-extension.ps1` → `artifacts\extension\shosa-win32-x64-<版>.vsix` (49.8 MB)。`tools\deploy-extension.ps1` は、それを作ってこの PC の VS Code に入れる
  (`-SkipPublish`: サーバーは前回のまま、`-NoPack`: 入れるだけ)。名前と引数は Calamo・Cantoria の `tools\` の 2 本に揃えた (ユーザー、2026-11-14)。
- **パッケージは置き場 (`artifacts\extension\stage`) で組み立てる。`editors\vscode` には `dist` のほか何も書かない。** はじめは `editors\vscode\server` に publish していたが、
  開発ホストがその `server\Shosa.Lsp.exe` を見つけて Debug の代わりに動かし (ビルドし直しても変わらない)、動いている間はパッケージを作り直せなくなった。
- **入れるとき**: 動いている言語サーバーの上には Windows が上書きさせないので、入れるのを断られたらインストール済みのサーバーを止めてやり直す
  (エディターは止められたサーバーを 4 回まで起動し直すので、通るまで止める。止められたウィンドウは「サーバーが止まった」と言う。Reload Window で新しいものが動く)。
  **断られる場面はまだ起きておらず、このやり直しは動かして確かめていない。** 入った後は、入ったサーバーが作ったものと同じファイルかを確かめる。
- **中身**: `dist\` (拡張、プレビュー、シンセのワークレット)、`server\` (言語サーバーと `shosa-music`)、色づけ、アイコン、README。
- **サーバーは .NET ランタイムごと入れる** (`dotnet publish -r <RID> --self-contained`)。入れる人に要るのは VS Code だけ (Lily# の拡張と同じ考え)。

- 拡張は `server\Shosa.Lsp.exe` (ほかの OS では `Shosa.Lsp`) を直接起動する。なければ今までどおり `.dll` を `dotnet` で (開発ホスト)。
- 確かめたこと: パッケージに入れた `server\shosa-music.exe` が `song.lys` を読むこと、`server\Shosa.Lsp.exe` が `initialize` に答えること。**`.vsix` を VS Code に入れて動かしてはいない。**
- `publisher` を `shosa-dev` から `yotsuda` に変えた (Lily# / Calamo / Cantoria と同じ)。
- **決まっていないこと (公開の前に要る)**: ライセンス (`LICENSE` がないので `--skip-license` で作っている。`shosa-music` は GPL で、同じ `.vsix` に入れて配るならその部分のソースの提供が要る)、

## 25. Kimodo を「清書」に使えるか: 資料の調査 (2026-11-14。動かしてはいない)

第 3 段階 (ROADMAP 3 節) の下調べ。NVIDIA の公式の文書 (`research.nvidia.com/labs/sil/projects/kimodo/docs/`)、リポジトリ (`github.com/nv-tlabs/kimodo`)、
モデルカード (`huggingface.co/nvidia/Kimodo-SOMA-RP-v1.2`) を、要約ツール越しに読んだ。**引用した数字と名前は、使う前に原文で確かめること。**

### 25.1 Kimodo が受け取るもの

入力は「文章 + 任意の制約」。制約は JSON の配列で渡す (`kimodo_gen "文章" --duration 5.0 --constraints constraints.json`。Python では `model(..., constraint_lst=[...])`)。
どれも `frame_indices` (0 始まりのフレーム番号、30 fps) で時刻を言う。

| 制約 | 中身 | Shosa の何にあたるか |
|---|---|---|
| `root2d` | 腰の床の上の道 `[x, z]` (メートル)。まばらな点でも、全フレームの道でもよい。向き `[cos, sin]` も付けられる | 求解器が出す骨盤の軌跡。`inplace` は動かない道 |
| `fullbody` | あるフレームの全身の姿勢: 関節ごとの回転 (軸と角度) と腰の位置 | イベントが着く瞬間の姿勢 (求解器の出力そのまま) |
| `left-hand` `right-hand` `left-foot` `right-foot` (`end-effector`) | 手首・かかとの位置と向き、指先・つま先の位置、腰の床の上の位置 | 腕の目標、接触 (`clap`、`b.hand`)、足の置き場所 |
| 足の接地 | 学習はしてあるが、**渡す口がまだない** (デモにも Python にもない) | 「どちらの足が床にあるか」は直接は渡せない。足の `end-effector` で代える |

- 座標は世界座標、Y が上、メートル。0 フレーム目の腰が床の原点、向きは `first_heading_angle` (既定は +Z 向き)。Shosa の座標 (y が上、z が向いている方向) と同じ向きで、原点を合わせるだけ。
- **制約はそのままでは厳密には守られない。** 生成の後の後処理 (足すべりの手直しと、制約に合わせる最適化) を通すと「ちょうど当たる」とされる。CLI では既定で入り、Python では `post_processing=True`。
- **制約の数は、種類ごとに 20 個未満が勧められている** (道は別)。モデルは「まばらな要所」で学習されていて、密な制約は道だけ。矛盾する制約は無視されるか、乱れる。
- 文章は必須 (空でよいかは書かれていない)。文章と制約の効き方は別々に重みを付けられる (`cfg_weight=[文章, 制約]`、既定は `[2.0, 2.0]`)。

### 25.2 出てくるもの

- 30 fps。**1 つの文章につき最長 10 秒。** それより長い動きは、文章を並べてつなぐ (`multi_prompt`。前の動きの最後のフレームから続きを作り、既定で 5 フレームのつなぎ)。
  つないだときに制約のフレーム番号がどの区間にかかるかは書かれていない。**ループの支援は書かれていない。**
- 出力 (NPZ): 関節の位置 `posed_joints`、回転行列 (親から・世界)、腰の軌跡、足の接地 `[左かかと, 左つま先, 右かかと, 右つま先]`、向き。
- 骨格は SOMA。モデルは 30 関節で考え、77 関節 (指つき) で出す。骨の長さは 1 人ぶんに決まっている。BVH を書ける (`--bvh`)。FBX・glTF はない。
- 1 回の生成は 1 人。まわりの物や相手は知らない。

### 25.3 動かすのに要るもの、ライセンス

- GPU: 全部を GPU に載せると 17 GB ほど。文章を読む部分 (Llama 3 8B + LLM2Vec) を CPU に回すと 3 GB 未満 (`TEXT_ENCODER_DEVICE=cpu`、少し遅い)。Linux で開発されていて、Windows は「Docker なら動くはず」。
  記事の実測では A100 で読み込み 35 秒、10 秒ぶんの生成 5.5 秒。
- **コードは Apache-2.0。重み (SOMA 版と G1 版) は NVIDIA Open Model License で、モデルカードに「商用に使える」とある。** 出力の権利を NVIDIA は主張しない、配るときは契約書の写しと断り書きを付ける、とされる
  (ライセンスの本文は要約で読んだ)。SMPL-X 版だけは研究用で、製品に使えない。
- **Llama 3 は Hugging Face で承認が要る。そのライセンスは読んでいない。** Shosa が配るのはコードだけで、重みは使う人が自分で取る形になるはず。
- Shosa の側は GPL に縛られない (Apache のコードを呼ぶだけ)。`shosa-music` と同じく、別のプログラムとして呼ぶ形が合う (Python と GPU が要るので、どのみち同じプロセスには入らない)。

### 25.4 Shosa から見た合い方

| | |
|---|---|
| **合う** | 拍をフレームに直して「このフレームでこの姿勢・この手の位置」と言える。腰の道を渡せる。後処理が足すべりも直す。商用に使える。BVH が出る |
| **手間がかかる** | 姿勢を SOMA の骨格の回転で渡す (Shosa の骨格 → SOMA への対応づけ。出力を戻すときも同じ)。10 秒を超えるクリップは区切ってつなぐ。文章を何にするか (Shosa には文章がない) |
| **合わない・分からない** | **制約は種類ごとに 20 個未満**: 120 拍/分の 10 秒は 20 拍で、1 拍ごとに姿勢を渡すともう上限。**ループがない** (`loop` のクリップは最初と最後に同じ姿勢を置くしかない)。足の接地を渡せない。2 人の接触 (握手、手拍子) は 1 人ずつ作って手の位置で合わせるしかない。制約がどれだけ守られるかの数字は文書にない |

いちばんの心配は、**Shosa の振付は「まばらな要所」ではない**こと。腕が 1 拍ごとに向きを変え、足が半拍ごとに動く動きを 20 個の要所に間引くと、振付そのものが変わる。
Kimodo が得意なのは「要所の間を自然に埋める」ことなので、効くのは攻撃の連携や身振りのような、要所が少なく間が長い動きのほうだろう (推測。試していない)。

## 26. 骨組みは省略できない: `figure` `dancer` `form` `score` (ユーザーが決定、2026-11-14。実装済み)

**12 節から 25 節に出てくる「`form` がなければ `section` ごとにクリップ」「1 人のファイルは段を `section` の直下に書く」「`section 名前 loop`」「`--clip`」は古い形**で、今はない。
全体は GRAMMAR_FOR_LLM.md の "A complete file" と "Scores: what a file writes"。

### 26.1 方針 (ユーザー)

- **省略できるキーワードをなるべく作らない。** 省略を許すと、ユーザーが文法の全体を理解するのが難しくなる。
  書く手間は、File > New のひな形に省略できない最低限の内容を入れることと、補完で支える。
- **Lily# の文法に慣れた人が違和感を持たないようにする。** Lily# では 1 つの `score` が 1 つの書き出しファイルに対応し、プレビューは 1 つの `score` を描いて切り替える。
- `title` `tempo` `time` `fps` は省略できてよい (`.lys` でも省略できる)。`form` と `score` は省略できない。語は `score` のまま (Lily# と役割が同じで、`music "song.lys" score karaoke` で並ぶ)。

### 26.2 決めたこと

| 決めたこと | 理由、Lily# との対応 |
|---|---|
| **`figure` と `dancer` は必須。段は必ず `figure` のブロックの中** (`solo { steps { … } }`)。直下に書くと `SH1003` | Lily# の `part` が必須なのと同じ。「1 人なら直下」という 2 つ目の文法がなくなった。`dancer` の `on FIGURE` も必須。`at` `facing` は `tempo` と同じ扱いで省略できる (原点、正面) |
| **`score` は必須 (1 つ以上)。`dancer 名前` を 1 人以上並べる** | Lily# の `score { staff melody }` と同じ形 (`staff` ↔ `dancer`)。並べていない踊り手は、その `score` に出ない。`score` がないと `SH1030`、踊り手がないと `SH1031` |
| **1 つの `score` が 1 つの書き出しファイル、1 本の動き。** 名前のない `score` は入力と同じ名前 (`walk.glb`)、`score Idle` は `walk-Idle.glb` | Lily# の規則そのまま (`<入力>-NAME`)。**「クリップ」という語は言語からなくなった** (C# の中の `MotionIr` / `MotionClip` は `score` 1 つぶんの動きのこと) |
| **`score` は `form` を 1 つ演じる。** 名前のない `score` は名前のない `form { }`、`form 名前` を書けばその `form`。演じる `form` がないと `SH1032` | Lily# と同じ。`form` を書かないことで「`section` ごとに別のクリップ」に切り替わる形はなくなった (`SH1018` もなくした) |
| **`loop` と `inplace` は `score` の中に書く** (`score Idle { dancer hero  form Idle  loop }`)。`section` の名前の後に書くと `SH1024` | つなぎ目や移動を抜くのは、書き出す動きの性質。「`form` で並べた `section` の `loop` は無視する」(13.9) という穴がなくなった。`form` が複数の `section` を並べていても効く |
| **ゲームのキャラクターのファイルは、動き 1 本につき `form` と `score` を 1 つずつ** (`samples/fighter.shosa`: 7 本で 14 行) | 1 `score` = 1 ファイルの帰結。長くなるが、どのファイルが書き出されるかが `score` の行を数えれば分かる |
| `music` のあるファイルだけは `form` を書かなくてよい | 曲の構成がそのまま構成になる (12.8)。書けば曲を並べ替える上書きで、省略による既定値ではない |
| `figure 名前 "ラベル"` のラベルはなくした。踊り手のいない `figure` を「既定の体」が踊ることもなくした | どちらも「書かなくても何かが補われる」仕組みだった |
| イベントの中の既定 (長さ 1 拍、`mid`、`@smooth`、小節線は任意) は残した | キーワードではなく記法。楽譜の既定の音価と同じ種類 |

退けた案: `score` に `form` を複数並べる (1 ファイルに複数のアニメーション。Lily# の「1 `score` = 1 ファイル」と食い違う)、

### 28.1 肘の向きを、姿勢から姿勢へ運ぶ (2026-11-14。実装済み)

`up` から `clap` へ下ろす途中で上腕が 1 フレームに 145 度ねじれる不具合 (`SkeletonTests.No_bone_flips_between_two_frames(name: "dance")`) を直した。

- **原因**: 肘の向きを、毎フレーム、決まった極 (`Rig.ElbowPole` = 下・後ろ・少し外) を「肩から手」の軸に直交する面へ落として決めていた。
  この決め方は、軸が極と平行になる 2 方向 (頭上のやや前・内と、その反対) で向きが定まらず、そこを通る手は肘が半回転する。`up` → `clap` の道はそこを通る。
- **どんな決め方でも、どこかに定まらない方向は残る** (球面上の接ベクトル場には零点がある)。極を動かしても零点が移るだけで、試した範囲では、届く範囲 (構え、胸の前) に来るか、いまの見た目 (構えで肘が下) を壊した。
- **直し方**: 肘の向きを極から決めるのは、**文面が名指しする姿勢 (各イベントの着く先) でだけ**にした。途中は、前の姿勢の肘の向きと次の姿勢の肘の向きを、それぞれ腕の軸と一緒に最短の回転で今の軸まで運び、
  進み具合で混ぜる (`Solver.cs` の `Carry` と `Across`。`Chain` が手の位置と肘の向きの組を運ぶので、途中で遮られた動きにも効く)。
  着いた姿勢の形は前と同じで、途中だけが変わる。零点の近くに「着く」姿勢は今も肘の向きがあいまいだが、止まっているので跳ばない。
- 確かめたこと: 試験 228 件が通る (上の 1 件を含む)。`arms { side.high up:2 clap:1/2 hold:1/2 }` を 0.05 拍刻みの連続写真で正面と横から見て、肘が外から下へなめらかに回る。VRM モデルではまだ見ていない。
- 膝にも同じ形の極 (`Rig.KneePole` = 前・少し外) があり、脚をまっすぐ前へ腰の高さに上げる道で同じことが起きうる。いまのサンプルと試験では出ていない。



## 29. 空の小節、小節で数える休み、`verse N { }` (ユーザーが決定、2026-11-14。実装済み)

27 節の 4 件のうち 2 件。全体は GRAMMAR_FOR_LLM.md の "Events" (小節線の項) と "Doing it again"。

### 29.1 空の小節は「その段が何も言わない 1 小節」(Lily# と同じ)

ユーザーの案: `| |` のように空っぽの小節を書いたら、そこは何もしない。16.6 と 27 節で退けていたが、採った。

- **規則**: 書かれた `|` はちょうど 1 小節を閉じ、何も入っていない小節は空の小節 (1 小節ぶんの `skip`。その小節の拍子の長さ)。
  Lily# の規則そのまま (`{ | | | | }` は空の小節 4 つ、`{ | c1 }` は空の小節の後に `c1`。Lily# の文法書で確かめた)。
- **線は飾りではなくなった。** 行の先頭の `|` も、`:0` の姿勢の直後の `|` (`guard:0 |`) も空の小節。区切りのつもりで書いていた `samples/fighter.shosa` の `Combo` と文法書の例は線を消した。
- 以前の反対 (行の先頭の線、`guard:0 |`、打ち間違いの `||` と区別がつかない) は、「今の文法との衝突」だった。できあがった姿で比べれば、Lily# と同じ規則 1 つで済むほうがよい。
  打ち間違いの `||` は黙って 1 小節増えるが、`check` の長さと、ほかの行との小節のずれで気づける。
- `%` は空の小節ももう一度行う (`| % |` は空の小節 2 つ)。

### 29.2 長い休みは `skip:10bar` / `hold:3bar`

- 長さの単位に `bar` を足した (`:0.3s` `:12f` と同じく、数に付けて書く)。`skip` と `hold` にだけ、小節の頭でだけ、整数で書ける。次の `|` がそれを閉じる (`%3` の後と同じ)。違反は `SH1033`。
- 曲の途中で拍子が変わっても、小節ごとにその拍子で数える。
- 退けた案 (ユーザーとの検討):

| 案 | 退けた理由 |
|---|---|
| `\| \| %10 \|` | `%N` は「直前の N 小節をもう一度」で、「1 小節を N 回」ではない (Lily# と同じ)。意味を変えると `vine:4 \| vine@mirror:4 \| %2 \|` と食い違う |
| Lily# の `R` / `R*3` を `skip` に当てる | `hold` も小節で数えたいので、綴りが 2 通りになる。小節の途中の `skip:2` は残るので `skip` に名前が 2 つできる。`R` (休符) は意味としては `hold` に近く、`skip` に当たるのは Lily# でも空の小節。大文字 1 字は Shosa の語彙から浮く |
| 空の小節だけ (数える書き方なし) | 試験では 12〜14 小節の休みが出ていて、`\| \| \| \| …` は数えにくい。Lily# も空の小節と `R*3` の両方を持つ |

### 29.3 `verse N { … }`: そのセクションが N 回目に演じられるときだけ

27 節の表の 1 つ目の案のとおり (Lily# の歌詞の `verse N { }` と同じ形)。

- 段の中に書く。`verse 2 { … }`、`verse 1,3 { … }`、`verse 1-2 { … }`。`verse` の外のイベントは毎回行う。
- **並んだ `verse` はひとつの場所を分け合う。** 場所の長さは、並んだもののうち最長 (演じない回のものも数える)。だから、その後ろは毎回同じ拍から始まる。どの `verse` も名指ししない回は、その場所で何も言わない。
- 「N 回目」は、書き出している `score` の中でそのセクションが演じられた回数 (曲があれば、曲がそのセクションを鳴らした回数)。練習用の `score` が Chorus を 1 回だけ演じるなら、そこでは `verse 1` が行われる。
- `verse` の中の `%` は、`verse` の前の小節を指せる (`a b | % | verse 1 { % | } verse 2 { c | }`)。
- 演じない回の `verse` も、長さと診断のために読む (出力には書かない)。この `score` では一度も来ない番号の `verse` に警告は出さない (別の `score` で来るかもしれない)。
- `move` の中には書けない (`SH1034`)。回を数えられるのはセクション。
- 実装: 構文は `SyntaxKind.Verse` (字句に `,` を足した。`1-2` は `1` と `-2` として読まれる。`form` の `[1-2. …]` と同じ)。`Binder.Verses` が並んだものをまとめて歩く。
- 確かめたこと: 5 回目の試験の「最後の A だけ、まん中の 1 人が最後の拍で跳ぶ」(被験者は 4 行を変え、`move` 2 つに持ち上げた) が、`steps` の最後の小節を
  `verse 1-2 { both.low both.mid both.low both.mid | } verse 3 { both.low both.mid both.low jump | }` にする 1 行の変更で書け、連続写真で 1 回目と 3 回目の違いを見た。

### 31.1 構文

- `section NAME {` の直後、最初のブロックより前にだけ書ける行 (`SyntaxKind.SectionItem`)。1 行に 1 つ。
- 「最初のブロックより前だけ」は構文の都合でもある: `tempo` `time` は直下のキーワードで、閉じ忘れたセクションの回復 (次の直下の項目で止まる) に使っている。
  ブロックの後の `upbeat N` は読んで、バインダーが `SH1036` で場所を言う。ブロックの後の `tempo` は、これまでどおり「`}` がない」になる。
- 26.1 の方針 (省略できるキーワードを作らない) との関係: この 3 行は「書かなければ既定値」ではなく「書かなければ変わらない」。ファイルの頭の `tempo` と同じ種類。

### 31.2 `tempo` `time`: 次に書くまで続く

- **セクションの小節の長さは、`form` がその前に何を演じるかで決まる。** `form { March Waltz Coda }` で `Waltz` が `time 3/4` を書けば、何も書かない `Coda` も 3/4。
  どこで演じても同じ拍子にしたいセクションは、自分で `time` を書く。ファイルの頭の `tempo` `time` は「`score` が始まるときの値」になった。
- テンポと拍子は別々に続く (`time` だけ書けばテンポはそのまま)。
- **拍の音符が変わるとき (4/4 → 6/8) にテンポを書かなければ、音楽の速さを保つ** (120 → 240)。21.1 の「テンポはその拍で数える」と同じ形で、曲から来る変化と数が合う。
  **ユーザーの確認待ち**: 数をそのまま保つ案 (8 分が前の 4 分と同じ長さになる) は退けた。
- `score` の `tempo N` は「ファイルが始まるテンポ」で、セクションのテンポは同じ比で変わる (曲のときの 21.1 と同じ規則)。
- `music` のあるファイルではセクションに `tempo` `time` を書けない (`SH1035`。曲のもの)。`upbeat` は書ける。
- セクションの途中の変化は書けないまま (セクションを分ける)。
- 実装: `BindClip` が演じる順に歩きながら地図 (`_tempos` `_meters`) を作り (`Change`)、`Place` でその場所を置く。あとは 21 節の仕組み (曲から来る地図) がそのまま働くので、求解器・出力・プレビューは変えていない。
  `SectionLength` は場所の拍子とテンポごとに覚える (同じセクションが 4/4 と 3/4 の両方で演じられると、空の小節や `skip:2bar` の長さが違う)。
  `shosa check` は曲のないファイルでも、変化があれば `score at 120 beats a minute (90 from beat 8), 4 to the bar (3 from beat 8): March 0-8 (2 bars), …` を言う。

### 31.3 `upbeat N`

- **弱起を使う段は、長さ N の小節で始める** (`arms { up:1 | side:3 | … }`)。それ以外の段はセクションの最初の小節線から始まる。
  見分けは「最初の小節線が閉じる小節の長さが N か」だけ (`BeginsWithUpbeat`。段を 1 回、何も書かずに歩いて測る)。長さが N でも 1 小節でもなければ、いつもの `SH1002`。
- セクションの長さは最初の小節線から数える。弱起は長さに入らない。
- **弱起は、その前に演じられるものの最後の N 拍に重なり、書いた部位だけを取る。** 優先順位の先頭に「何番目に演じられるか」を足した (`[play, 幅, 段の番号, …]`)。
  後に演じられるものが勝つので、前のセクションの狭い段 (`leftArm`) にも弱起の `arms` が勝つ。同じ回の中は今までどおり (狭い段、後の行)。
  歩は切れないので、重なった前のセクションの歩は取られない (13.2 の規則のまま)。`skip` は何も取らない。
- **`score` の頭より前には何もない**: 0 拍より前のイベントは 0 拍に寄せる (長さ 0 = `:0` の姿勢と同じ扱い)。体は弱起が終わった姿で始まる。
  **ループでは終わりに回す**: 0 拍より前に始まるイベントを 1 周ぶん後ろへずらし、最後に演じられるものにも勝たせる (`Wrap`)。
- 曲の弱起 (`SectionIr.Pickup`) とは別のもの。曲に弱起があり、最初のセクションに `upbeat` を書けば、踊りの弱起は曲の弱起の上に乗る (0 拍より前に出ない)。
- N は 1 小節より短い (`SH1036`)。
- 長さ 0 の跳躍 (頭の弱起に書いた `jump.apart`) で人形が消えた (滞空 0 秒で NaN)。跳び終えた姿で立つように直した。

### 33.1 規則

- Lily# の `form` にはない書き方。Lily# に慣れた人が読んで意味を取り違える形ではない (`tempo` `time` は同じ語)。

退けたまま残したもの: **段のないセクション** (`section Faster { tempo 132 }`) は今も受け付けられ、長さ 0 で後ろのテンポを決める。

### 33.2 構文と実装

## 35. テンポの 3 つの書き方 (`N`、`N%`、`音符 = N`) と `check` の言い方 (ユーザーが決定、2026-11-15。実装済み)

| 決めたこと (ユーザー) | 中身 |
|---|---|
| **`tempo N%` を、`tempo` を書ける所すべてに** (退けた案: `score` だけ、足さない) | 意味は 1 つ: 「この行がなければそこで有効だったテンポの N%」 |
| **`tempo 4. = 60` (Lily# と同じ、音符 = 数)** (退けた案: 足さない、6/8 の拍を付点 4 分にする) | 数だけの `tempo 180` は今までどおり拍 (拍子の下の数の音符) の数。拍の長さと小節の数え方は変えない |
| **`check` はセクションごとに 1 行** (退けた案: 今の 1 行に足す、今のまま) | 拍の範囲、小節、秒、テンポ、拍子 (`N/N`)。`score` の行に全体の拍と秒 |

### 35.1 規則

- **書き方は場所によらず同じ 3 つ**: ファイルの頭、セクションの頭、`form` の名前の前、`score`。「`N` と書ける所には `N%` と `音符 = N` を書ける」。
- **`N%` の「この行がなければ」**は場所ごとにこうなる:

  | 場所 | 何の N% か |
  |---|---|
  | `score` | その `score` が始まるはずだったテンポ (32 節の「実際に始まるテンポ」と同じ求め方)。後のテンポも同じ比で変わる |
  | セクションの頭 | その前に有効だったテンポ (`time` で拍の音符が変われば、音楽の速さを保った後の値) |
  | `form` の名前の前 | その回が演じられるはずだったテンポ。セクション自身が `tempo` を書いていればその N% (`tempo 120` の March に `tempo 110% March` で 132)、書いていなければ前から続くテンポの N% |

- **比はその場で数になり、後は 31 節の「次に書くまで続く」のまま。** 規則は増えていない。

  同じ行頭に `time` を書いていれば、その新しい拍子で直す (`form { tempo 4. = 80 time 6/8 Six }` は 240)。`score` の `音符 = N` は、その `score` が始まる拍子で直す。
- できあがった値は 10〜400 (`SH1001`。`音符 = N` と `N%` は場所が決まってから検査する。`score` が全体を遅くする比は検査に入れない)。
- 曲のあるファイルの `form` とセクションには、`N%` も書けないまま (`SH1035`。曲の途中だけ速さを変えることになるので、曲の再生の仕組みが要る)。
